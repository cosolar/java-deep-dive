## 为什么有这个项目

市面上的 Java 资料，大多逃不开两种极端：

- **面试八股**：背得滚瓜烂熟，一问「为什么」就卡壳。比如「HashMap 底层是数组+链表+红黑树」——那为什么容量必须是 2 的幂？为什么树化阈值是 8？
- **官方文档**：准确但零散，看完不知道「这东西在真实项目里怎么用、会在哪里炸」。

这个项目想填中间那道沟：**每讲一个知识点，都回答三个问题——它的原理是什么、源码里怎么实现的、生产上会在哪里翻车。**

举几个例子：

| 常见资料 | 这里怎么讲 |
|---|---|
| 「Spring 事务基于 AOP」 | 为什么**同类自调用**事务会失效？三种解法分别的代价是什么？ |
| 「用 Redis 做分布式锁」 | 锁超时了业务还没执行完怎么办？RedLock 到底靠不靠谱？ |
| 「HashMap 线程不安全」 | JDK 7 头插法为什么会**死循环**？JDK 8 改成尾插后为什么还是不安全？ |
| 「MVP 是最小可行产品」 | 它和「功能残缺的半成品」的本质区别是什么？Dropbox 当年怎么用一个视频验证需求？ |

## 这不是什么

为了避免误解，先说清楚边界：

- **不是面试题库**。虽然每篇都有「面试高频问法」，但那是用来检验理解的，不是让你背答案。
- **不是 API 手册**。不会告诉你 `StringUtils` 有多少个方法，但会告诉你字符串拼接为什么在循环里要避免。
- **不吹任何技术**。讲敏捷也讲「什么情况不该用敏捷」，讲微服务也讲「什么时候单体更合适」。

## 亮点

### 1. 每篇都是「原理 → 源码 → 坑点 → 面试」四段式

不是知识点罗列，而是完整的认知闭环。以《集合框架源码》为例：

- **原理**：数组 + 链表 + 红黑树，为什么要扰动函数
- **源码**：`putVal` 六个步骤逐行注释、`resize` 的「一分为二」优化
- **坑点**：可变对象当 key、并发丢数据、初始容量给错
- **面试**：11 道题，每题「一句话结论 + 展开 + 加分点」

### 2. 源码级实证，不是二手转述

讲框架必给**具体类名和方法**，让你能顺着去读源码：

- Spring AOP → `JdkDynamicAopProxy` / `CglibAopProxy`
- Spring MVC → `DispatcherServlet.doDispatch` 的四个提前 return
- MyBatis → `MapperProxy.invoke` 怎么把方法调用转成 SQL
- Sentinel → `ProcessorSlotChain` 的责任链
- Raft → 选举限制为什么能防止脑裂

### 3. 400 张 Mermaid 图，全部可编辑

不是截图，是文本化的矢量图——你可以直接改。涵盖类图、时序图、状态机、流程图。

### 4. 123 篇按「学习依赖」排序，不是按热度堆砌

从「语言」到「AI」，形成一条完整路径。你不会在不懂 JVM 的时候被丢去读分布式事务。

### 5. 敢讲「不该用什么」

- 什么情况**不该**用敏捷（客户不参与、需求锁死）
- 什么情况**不该**用微服务（团队太小、业务简单）
- 什么情况**不该**用 LLM（强一致、成本不划算）

技术选型最缺的不是「怎么用」，是「什么时候别用」。

| 你是谁 | 能收获什么 |

## 贡献

欢迎提 Issue 和 PR。特别欢迎这几种：

- **纠错**：技术细节有误、源码引用过时（Java 版本迭代快）
- **补坑**：你在生产环境踩过、但文章没覆盖的坑
- **新增篇目**：按现有文章的结构写，保持「原理 → 源码 → 坑点 → 面试」四段式

提交前请确认：

1. 技术细节有依据（能给出源码位置或官方文档）
2. Mermaid 图语法正确（中文 label 用英文引号包裹）
3. 面试题至少 10 道，每题有「一句话结论 + 展开 + 加分点」
