## 三、Java 基础与集合

### 1. HashMap 容量为什么是 2 的幂？（阿里一面、美团一面）

**结论**：为了用 `(n - 1) & hash` 代替取模，并且扩容时元素要么留在原位、要么移到「原位置 + oldCap」，减少 rehash 计算。

**展开**：`n` 是 2 的幂时，`n-1` 的低位全是 1，按位与等价于取模且更快；扩容到 `2n` 时，只需看 hash 的第 `log2(n)` 位：0 留原位，1 移到 `i + oldCap`。这也解释了为什么容量必须补成 2 的幂（`tableSizeFor`）。

**加分点**：说出「hash 高低 16 位异或」是为了让高位也参与桶下标，减少碰撞；并指出容量过大会浪费、过小会频繁扩容。

**业务落地**：订单号、缓存 key、路由分片都常见 String；容量按 2 的幂预估，能减少扩容与碰撞。

**追问**：为什么负载因子是 0.75？树化阈值为什么是 8/6？扩容为什么是 2 倍？

### 2. 红黑树和 AVL 的区别？为什么 HashMap 用红黑树？（阿里一面、美团一面）

**结论**：AVL 更严格平衡（高度差 ≤1），查找略快但插入/删除旋转多；红黑树放宽平衡（最长路径 ≤ 2 倍最短），旋转少，综合插入删除更稳。

**展开**：HashMap 冲突链表化后主要是插入/删除与查找混合；红黑树用颜色约束换取更少调整。TreeMap 也用红黑树，因为要维护有序。

**加分点**：说出「链表长度 8 转树、降到 6 退回链表」是为了避免频繁转换；树化还要求容量 ≥64，否则先扩容。

**业务落地**：TreeMap 适合区间查询、排行榜、按 key 范围扫描；选择结构先看“查、插、删、范围”四个操作。

**追问**：为什么内存索引多用红黑树而不是 B 树？红黑树最坏高度是多少？

### 3. 重载和覆盖的区别？返回值不同能重载吗？（字节二面）

**结论**：重载看「方法名 + 参数列表」，返回值不参与；返回值不同不能构成重载。覆盖是子类重写父类同签名方法，返回值必须兼容（协变）。

**展开**：重载是编译期静态分派；覆盖是运行期动态分派（`invokevirtual`）。`static`、`private`、`final` 方法不能被覆盖。

**加分点**：提到「泛型擦除后，`List<String>` 与 `List<Integer>` 参数不能重载」——签名擦除后相同。

**业务落地**：接口多版本兼容、SDK 重载常用；但重载太多会让调用方困惑，生产更推荐不同方法名。

**追问**：泛型擦除后桥方法怎么生成？编译期分派和运行期分派分别发生在哪一步？

### 4. String 的 equals 怎么实现的？hashCode 相同对象就相同吗？（百度一面）

**结论**：`String.equals` 先比引用，再比长度，再逐字符（JDK 9+ 比 `byte[]`/coder）；`hashCode` 相同只能说明桶相同，不代表相等。

**展开**：`"a".hashCode()` 与另一个不同字符串可能碰撞；所以 HashMap 必须先比 hash 再 `equals`。重写 `equals` 必须重写 `hashCode`。

**加分点**：说出「String 不可变才能缓存 hash，并把 hash 存进字段」。

**业务落地**：缓存 key、去重、幂等键都依赖 equals/hashCode；自定义对象做 key 必须同时重写两者。

**追问**：字符串常量池和 intern 是什么关系？哈希碰撞攻击怎么防？

### 5. `==` 和 `equals` 的区别？Integer 缓存有什么坑？（百度、美团）

**结论**：`==` 比引用/基本值，`equals` 默认比引用，可重写为值比较；`Integer` 的 `-128~127` 走缓存，超出范围 `==` 为 false。

**展开**：`Integer a=127,b=127` 为 true；`128` 为 false。自动装箱在循环里还会创建对象。

**加分点**：提到「用 `equals` 或先拆箱比基本类型；`Objects.equals` 防空」。

**业务落地**：金额、状态、ID 比较避免用 ==；包装类型比较优先 Objects.equals 或先拆箱。

**追问**：Integer 缓存范围为什么是 -128~127？valueOf 和 new Integer 有什么区别？
## 四、并发与 JVM

### 6. 进程和线程的区别？哪个效率高？（字节一面）

**结论**：进程有独立地址空间，线程共享进程资源；线程切换/通信更轻，但隔离性差。效率取决于场景，不是绝对。

**展开**：进程间通信要 IPC（管道、共享内存、Socket）；线程共享堆、独立栈/寄存器。线程崩溃可能拖垮进程；进程崩溃隔离更好。

**加分点**：结合 Java 说「线程是 JVM 调度的基本单位，虚拟线程进一步降低阻塞成本，但不改变共享内存模型」。

**业务落地**：请求隔离、超时控制、故障边界都与进程/线程模型有关；线程池不是越多越好。

**追问**：虚拟线程解决了什么？为什么它不改变共享内存模型？上下文切换成本在哪？

### 7. 死锁的四个条件和解决办法？（字节一面）

**结论**：互斥、占有并等待、不可抢占、循环等待；破坏任一即可，工程上最常用「固定加锁顺序 + 超时」。

**展开**：`tryLock(timeout)` 打破无限等待；按资源 ID 排序加锁打破循环；减少锁粒度/无锁结构降低概率。

**加分点**：会看 `jstack` 里的 `found one Java-level deadlock`，并能定位到具体锁与线程。

**业务落地**：数据库死锁、锁顺序、连接池耗尽都可能表现为“线程卡死”；先看 jstack 再看 DB 锁。

**追问**：jstack 里 deadlock 怎么读？tryLock 超时如何打破循环等待？

### 8. 线程池参数与执行流程？（阿里二面、美团二面）

**结论**：`corePoolSize` → 队列 → `maxPoolSize` → 拒绝策略；不是「先扩到 max 再排队」。

**展开**：核心线程满后先入队；队列满才扩到 max；再满执行拒绝策略。`allowCoreThreadTimeOut` 可回收核心线程。

**加分点**：说出「无界队列会让 max 失效」；CPU 密集设 N+1，IO 密集按阻塞系数估算；生产用有界队列 + 自定义拒绝策略 + 监控。

**业务落地**：Web 容器、异步任务、批量任务要分别建池；不要用一个池扛所有流量。

**追问**：无界队列为什么让 max 失效？拒绝策略怎么选？核心线程数怎么估？

### 9. synchronized 和 ReentrantLock 的区别？（美团一面）

**结论**：前者 JVM 内置、自动释放、非公平（可偏向/轻量升级）；后者 API 层、可中断/超时/公平/多条件队列，必须手动 `unlock`。

**展开**：JDK 24 起虚拟线程在 `synchronized` 内阻塞不再钉住载体线程（JEP 491），但锁竞争仍在；临界区要短。

**加分点**：说出「`ReentrantLock` 忘 unlock 是生产事故；用 try-finally 或 try-with-resources 封装」。

**业务落地**：库存扣减、状态变更等临界区要短；锁内不要做 RPC、不要写日志到磁盘。

**追问**：锁升级过程是什么？JEP 491 解决了虚拟线程什么问题？公平锁代价是什么？

### 10. ThreadLocal 原理与内存泄漏？（美团二面、字节一面）

**结论**：每个 `Thread` 持有一个 `ThreadLocalMap`，key 是弱引用的 `ThreadLocal`，value 强引用；线程池长存活时，key 被回收而 value 留住，造成泄漏。

**展开**：`set` 以 `ThreadLocal` 为 key；`remove` 清理 Entry。线程池场景必须在 `finally` 里 `remove`。

**加分点**：解释「为什么 key 用弱引用」——若强引用，ThreadLocal 对象本身也无法回收；但这不能替代 remove。

**业务落地**：用户上下文、TraceId、租户信息常放 ThreadLocal；线程池复用必须 finally remove。

**追问**：InheritableThreadLocal 有什么坑？TransmittableThreadLocal 解决什么？

### 11. JVM 线上 Full GC 频繁怎么排查？（字节、阿里）

**结论**：先看 GC 频率与老年代增长（`jstat -gcutil`），再 dump 堆（`jmap`/`jcmd`），用 MAT 找支配对象，最后回到代码/流量/缓存。

**展开**：区分「内存泄漏」（老年代持续上涨）与「容量不足/大对象」（峰值高）；看 Full GC 后老年代是否回落。常见根因：本地缓存无上限、大查询一次性加载、ThreadLocal 累积、元空间/CodeCache 满。

**加分点**：先止血（限流/扩容/重启）再定位；保留 dump 与 GC 日志；别只看「GC 耗时 10ms」——可能是 GC 后缓存穿透导致 10 秒卡顿。

**业务落地**：订单服务 FullGC 先看老年代是否回落；本地缓存无上限、批量查询、ThreadLocal 是常见根因。

**追问**：G1 日志怎么看 Humongous？什么情况该换 ZGC？MAT 里怎么找 GC Roots？

### 12. 类加载过程？一个类能被加载两次吗？（奇安信二面）

**结论**：加载 → 验证 → 准备 → 解析 → 初始化；同一个类加载器不能重复加载同名类，不同加载器可以（彼此隔离）。

**展开**：双亲委派保证核心类不被篡改；`defineClass` 重复定义抛 `LinkageError`；热部署/OSGi 用不同 ClassLoader 实现「同名不同类」。

**加分点**：说出「类的唯一性 = 类加载器 + 全限定名」，这也是 Tomcat 多应用隔离的原理。

**业务落地**：插件化、热部署、Tomcat 多应用隔离都靠类加载器；同名类不同加载器不是同一个类。

**追问**：双亲委派被破坏的典型场景？SPI 为什么需要线程上下文类加载器？
## 五、MySQL

### 13. 为什么索引用 B+ 树，不用 B 树/哈希/有序数组？（美团、百度）

**结论**：磁盘按页读，B+ 树扇出大、树高低，3-4 层可索引亿级数据；叶子链表支持范围查询；哈希不支持范围，有序数组增删代价高。

**展开**：B+ 树非叶子只存键，能放更多索引项；数据都在叶子，查询稳定。InnoDB 聚簇索引叶子存整行，二级索引叶子存主键。

**加分点**：能算「16KB 页、每键 8B+指针 6B，一层约 1000 个键，三层约 10 亿」。

**业务落地**：MySQL 索引、文件系统、数据库页都利用“页读 + 高扇出”；理解页大小才能算树高。

**追问**：16KB 页能放多少键？三层 B+ 树能索引多少行？聚簇索引和二级索引叶子差什么？

### 14. 聚簇索引和非聚簇索引、回表、覆盖索引、索引下推？（美团二面、百度一面）

**结论**：聚簇索引叶子存行数据；二级索引叶子存主键，查非索引列要回表。覆盖索引避免回表；索引下推把 `where` 条件下推到存储引擎过滤。

**展开**：`explain` 看 `type/key/rows/Extra`；`Using index` 是覆盖索引，`Using index condition` 是索引下推。回表次数多时，覆盖索引或调整索引顺序更有效。

**加分点**：说出「`select *` 最容易回表；联合索引把过滤性强的列放前面，但要看最左匹配」。

**业务落地**：慢查询先 explain，再看回表次数；覆盖索引与索引下推是最常用的两个优化。

**追问**：什么情况索引失效？回表成本怎么估？索引下推一定更快吗？

### 15. 三个单列索引 a、b、c，`where a and b and c` 用哪个？（美团二面）

**结论**：通常只用其中一个（优化器按代价选），其余条件在回表后过滤；MySQL 5.6+ 也可能走 index merge（交集），但不保证。

**展开**：单列索引各自只能定位一个条件；联合索引 `(a,b,c)` 才能同时利用三个条件。优化器会估算行数与回表成本。

**加分点**：用 `explain` 验证，而不是背「一定用 a」；`index merge` 出现说明优化器认为合并更便宜。

**业务落地**：多条件查询不要指望多个单列索引；联合索引的顺序要按过滤性与最左匹配设计。

**追问**：index merge 为什么不一定好？优化器如何估算行数？

### 16. RR 隔离级别下还有幻读吗？MVCC 和间隙锁怎么配合？（美团二面）

**结论**：快照读靠 MVCC 的 Read View 看不到新插入行；当前读（`for update`/`update`/`delete`）靠 next-key lock（记录锁 + 间隙锁）阻止插入。因此 InnoDB 在 RR 下基本解决幻读，但不是「所有读都无幻」。

**展开**：MVCC 用隐藏字段（`trx_id`、`roll_ptr`）+ undo log + Read View；RC 每次读生成 Read View，RR 事务内复用。间隙锁只在 RR 存在（RC 没有），锁的是索引区间。

**加分点**：指出「先快照读、后当前读」可能看到变化；`select ... lock in share mode` 也是当前读。

**业务落地**：库存、转账、订单状态在 RR 下要区分快照读与当前读；当前读才受 next-key lock 保护。

**追问**：RC 下为什么没有间隙锁？next-key lock 锁的是索引还是行？

### 17. 主键为什么不能太大？（字节二面）

**结论**：二级索引叶子存主键，主键越大，索引越占空间、页分裂越频繁、缓存命中越低；整型自增主键最优。

**展开**：UUID 作主键无序，插入随机导致页分裂与碎片；字符串主键比较慢。自增主键顺序写入，页利用率高。

**加分点**：说出「雪花 ID 是趋势递增，但要注意 JS 精度，返回前端用字符串」。

**业务落地**：订单主键建议自增 BIGINT 或趋势递增雪花；主键越大，二级索引和页分裂成本越高。

**追问**：UUID 为什么不适合做主键？雪花 ID 怎么做趋势递增？
## 六、Redis 与缓存

### 18. Redis 为什么快？单线程还是多线程？（字节二面）

**结论**：纯内存、数据结构高效、命令执行单线程避免锁竞争、epoll 多路复用、IO 多线程处理网络读写；不是「所有环节都单线程」。

**展开**：Redis 6 起网络 IO 多线程，命令执行仍单线程；慢命令（`keys *`、大 `hgetall`）会阻塞。持久化、删除大 key 用后台线程/子进程。

**加分点**：说出「单线程的瓶颈在 CPU 与网络，不在锁；分片集群横向扩展」。

**业务落地**：Redis 快不代表任何命令都快；big key、keys、hgetall 都可能阻塞。

**追问**：Redis 6 的 IO 多线程改了什么？单线程瓶颈在哪？

### 19. 用 `SET NX EX` 实现分布式锁有什么问题？（美团一面）

**结论**：超时误删、不可重入、锁等待/自旋、主从切换丢锁、续期复杂。

**展开**：解锁要用 Lua 比对 value 再删；超时时间要覆盖业务或加续期（看门狗）；主从异步复制下，主挂后备节点可能没有锁；Redlock 有争议，强一致场景用 ZooKeeper/etcd。

**加分点**：说出「锁的价值是减少并发，不是保证绝对互斥；最终一致性要靠幂等与唯一约束兜底」。

**业务落地**：分布式锁用于减少并发，不是正确性的唯一来源；最终要靠 DB 条件更新/唯一约束兜底。

**追问**：Redlock 争议在哪？watchdog 续期怎么做？fencing token 解决什么？

### 20. 缓存穿透、击穿、雪崩分别怎么解决？（字节、美团）

**结论**：穿透=查不存在的数据，用布隆过滤器/空值缓存；击穿=热点 key 失效，用互斥重建/逻辑过期；雪崩=大量 key 同时失效，用过期时间加随机 + 多级缓存 + 降级。

**展开**：布隆有假阳性、不能删除；空值要设短 TTL；互斥锁要防死锁；逻辑过期用异步重建，牺牲短期一致性换可用性。

**加分点**：说出「限流/降级是最后一道，不要只靠缓存」。

**业务落地**：商品详情、首页缓存要同时防穿透、击穿、雪崩；三套手段不要混为一谈。

**追问**：布隆过滤器为什么不能删除？逻辑过期怎么保证不返回过期数据？

### 21. Redis 和 MySQL 双写一致性怎么做？（美团二面）

**结论**：常用 Cache Aside：读未命中查库回填；写先更新库再删缓存；删失败用消息/订阅补偿；强一致要求高时用延迟双删或 binlog 订阅。

**展开**：先删缓存再更新库，在并发读下会把旧值回填；更新库后删缓存仍有短暂不一致。可接受最终一致时，用 binlog 订阅/CDC 异步补偿 + 版本号/过期时间兜底；**缓存方案本身给不了强一致**，强一致要靠事务、锁或串行化，代价是吞吐。

**加分点**：指出「双写不是原子操作，别承诺强一致；对账与补偿才是闭环」。

**业务落地**：价格、库存、用户资料适合 Cache Aside；强一致要求高时用 binlog/事务消息补偿。

**追问**：延迟双删为什么要“延迟”？先删缓存再更新库为什么会脏读？
## 七、Spring 与 MQ

### 22. Spring 事务多条 SQL 为什么用同一个连接？（美团二面）

**结论**：事务期间连接绑定到线程（`TransactionSynchronizationManager` + `ThreadLocal`），`DataSourceUtils.getConnection` 从当前事务上下文取同一连接。

**展开**：`@Transactional` 通过 AOP 开启事务，把 `ConnectionHolder` 绑定到线程；MyBatis/JPA 从同一上下文取连接。跨线程/异步会丢事务。

**加分点**：说出「同类自调用导致事务失效」也是 AOP 代理未生效；异步线程要显式传递事务上下文或拆事务。

**业务落地**：事务失效常见于自调用、异步线程、异常被吞、非 public 方法；先确认代理是否生效。

**追问**：TransactionSynchronizationManager 怎么绑定连接？异步线程怎么传事务？

### 23. 消息队列怎么选？Kafka、RocketMQ、RabbitMQ 区别？（美团、字节）

**结论**：Kafka 高吞吐、日志/流处理；RocketMQ 事务消息、顺序消息、延迟消息，Java 生态友好；RabbitMQ 轻量、路由灵活、低延迟，但吞吐较低。

**展开**：Kafka 分区顺序、零拷贝、KRaft；RocketMQ 半消息+回查、延迟等级；RabbitMQ Exchange/Queue 模型、Quorum Queue。

**加分点**：按「吞吐/延迟/事务/顺序/延迟消息/运维成本」做表，而不是只报名字。

**业务落地**：订单通知要可靠 + 可重试 + 幂等；事务消息适合“本地事务 + 发消息”强绑定场景。

**追问**：RocketMQ 事务消息的回查怎么做？Kafka 能替代吗？

### 24. Kafka 为什么快？零拷贝怎么实现？（奇安信一面）

**结论**：顺序写磁盘、页缓存、批量+压缩、分区并行、零拷贝（`sendfile`）减少用户态/内核态拷贝。

**展开**：生产者批量发送，Broker 顺序追加；消费者拉取连续段。零拷贝让数据从页缓存直接到网卡，跳过用户态缓冲。

**加分点**：说出「零拷贝不是不拷贝，是减少拷贝次数与上下文切换」。

**业务落地**：日志采集、流处理选 Kafka；业务通知、延迟消息选 RocketMQ；轻量路由选 RabbitMQ。

**追问**：零拷贝减少了哪几次拷贝？页缓存为什么比应用缓存更有效？

### 25. 消息消费失败怎么办？三笔订单没消费怎么补？（奇安信一面）

**结论**：重试 + 死信队列 + 补偿任务；补单要幂等（业务唯一键/唯一索引），先查后补，避免重复。

**展开**：区分可重试（网络/超时）与不可重试（参数/业务拒绝）；死信人工处理；补偿用定时任务扫「未完成状态」表，状态机驱动。

**加分点**：说出「消费失败不是重启消费者就好，要有对账与告警」。

**业务落地**：消费失败先分类：可重试/不可重试；死信队列 + 补偿任务 + 对账是闭环。

**追问**：重试次数怎么定？死信消息怎么人工处理？怎么防重复消费？
## 八、系统设计与场景

### 26. 设计秒杀：怎么防超卖？QPS 从 1 万到 100 万怎么改？（阿里、字节）

**结论**：静态化 + CDN + 限流 + Redis 预扣（Lua 原子）+ MQ 异步下单 + DB 唯一约束/乐观锁兜底；超卖靠「原子扣减 + 唯一约束 + 对账」。

**展开**：1 万级：网关限流 + Redis 扣库存 + 异步落库；100 万级：多级缓存、库存分片、答题/验证码削峰、独立集群、压测与降级开关。

**加分点**：说出「Redis 扣减成功不代表订单成功，要有失败回补与对账」。

**业务落地**：秒杀核心是“原子扣减 + 唯一约束 + 回补 + 对账”；缓存只是第一层。

**追问**：Redis Lua 和分布式锁的区别？Redis 扣成功但订单失败怎么办？

### 27. 1000 万商家，首页怎么加载附近商家？（美团二面）

**结论**：地理索引 + 分桶缓存：Redis GEO/GEOSEARCH 或 ES `geo_distance`，按 geohash 前缀分桶，查询时先算附近格子再过滤；热点区域缓存结果。

**展开**：商家坐标写 Redis GEO；用户位置 geohash 编码取邻域 9 格；按距离排序分页；1000 万数据按城市/区域分片，避免单 key 过大。

**加分点**：说出「geohash 边界问题要取邻域；排序与分页在服务端做，别全量拉回」。

**业务落地**：附近商家用 GEO/ES + geohash 邻域；热点区域缓存结果，分页排序在服务端做。

**追问**：geohash 边界问题怎么处理？1000 万商家怎么分片？

### 28. 流量猛涨，加节点还没起来就被打爆，怎么办？（美团二面）

**结论**：先限流保命，再分批扩容与预热，最后查瓶颈（连接池/线程池/下游配额）。

**展开**：网关限流/排队；新节点延迟注册、就绪探针通过后再接流量；JVM/连接池预热；数据库连接数与下游配额先扩，否则加机器只是把压力传下去。

**加分点**：说出「扩容不是线性：DB、Redis、第三方配额往往是瓶颈」。

**业务落地**：扩容前先看 DB 连接、Redis、下游配额；新节点要预热、就绪后再接流量。

**追问**：为什么加机器后更慢？就绪探针和注册延迟怎么配合？

### 29. 订单 30 分钟未支付自动取消，千万级怎么跑？（字节二面）

**结论**：不要全表轮询；用延迟消息/时间轮/Redis ZSet 到期触发，配合状态机与幂等。

**展开**：下单写延迟任务（RocketMQ 延迟消息、Redis ZSet、Kafka + 时间轮）；到期消费者查状态，未支付则取消并回补库存；分片扫描只作兜底。

**加分点**：说出「延迟消息可能重复/丢失，取消要幂等，库存回补要有对账」。

**业务落地**：延迟消息/时间轮/Redis ZSet 触发取消；状态机 + 幂等 + 库存回补。

**追问**：延迟消息丢了怎么办？重复取消怎么防？

### 30. 设计一个论文查重系统（阿里一面）

**结论**：分词/指纹 → 相似度 → 倒排索引召回 → 阈值判定；用 shingling/MinHash/SimHash 降维，避免两两比对。

**展开**：按句/段落切分，构造 k-shingle 集合；MinHash 估算 Jaccard；SimHash 算海明距离；倒排索引按指纹召回候选；阈值结合人工复核。

**加分点**：说出「查重不是字符串相等，要处理改写/同义/引用；大规模要分桶与近似」。

**业务落地**：查重先分词/指纹，再召回候选，最后算相似度；不要两两比对。

**追问**：SimHash 和 MinHash 区别？阈值怎么定？倒排索引怎么召回？

### 31. 雪花算法结构？订单 ID 长度合适吗？（飞猪一面）

**结论**：1 位符号 + 41 位时间戳 + 10 位机器 + 12 位序列；19 位十进制，JS 精度只有 53 位，返回前端要用字符串。

**展开**：41 位约 69 年；10 位机器可分 1024 个；12 位每毫秒 4096 个。时钟回拨要处理（等待/报错/备用位）。

**加分点**：说出「趋势递增对 B+ 树友好，但别依赖严格递增做业务排序」。

**业务落地**：雪花 ID 趋势递增，适合 B+ 树；返回前端用字符串，避免 JS 精度丢失。

**追问**：时钟回拨怎么处理？机器位不够怎么办？

### 32. JDK 8、17、21 的主要区别？（飞猪一面）

**结论**：8 是 Lambda/Stream/新时间；17 是 Record/Sealed/文本块/模式匹配（部分）；21 是虚拟线程、分代 ZGC、Record 模式、switch 模式。

**展开**：17 是 LTS，生态成熟；21 的虚拟线程适合 IO 密集；25 进一步修 pinning、加 Scoped Values。

**加分点**：说出「升级先看 GC 默认值、`javax/jakarta`、框架兼容矩阵」。

**业务落地**：升级先看 GC 默认、javax/jakarta、框架兼容；虚拟线程适合 IO 密集，不适合 CPU 密集。

**追问**：JDK 21 虚拟线程怎么用？ZGC 分代有什么变化？

### 33. CMS、G1、ZGC 的区别？（飞猪一面）

**结论**：CMS 老年代并发标记清除、碎片化、已废弃；G1 分 Region、可预测停顿、整堆回收；ZGC 染色指针 + 并发整理，停顿毫秒级，适合大堆。

**展开**：G1 的 Young/Mixed GC、Humongous 对象；ZGC 分代在 23 成为默认；CMS 在 9 弃用、14 移除。

**加分点**：说出「低延迟选 ZGC，吞吐与可控停顿选 G1，别用 CMS」。

**业务落地**：低延迟大堆看 ZGC，吞吐/可控停顿看 G1；CMS 已废弃，不要再作为新系统选项。

**追问**：G1 的 Mixed GC 什么时候触发？ZGC 染色指针解决什么？

### 34. 怎么统计下游失败率又不影响接口性能？（虎鲸一面）

**结论**：异步 + 滑动窗口 + 无锁计数：`LongAdder` 累加成功/失败，定时窗口汇总；采样与本地缓冲，避免同步远程上报。

**展开**：按时间片（如 10s）滚动；高并发用 `LongAdder` 分散热点；上报异步批量；监控告警用聚合值，不逐请求写日志。

**加分点**：说出「失败率要区分错误类型与超时，别把业务拒绝算成系统失败」。

**业务落地**：监控失败率要异步、采样、分错误类型；不要同步远程上报拖慢接口。

**追问**：LongAdder 为什么比 AtomicLong 快？滑动窗口怎么实现？

## 九、答题模板：把「背过」变成「会答」

1. **先给结论**：一句话说清是什么/怎么做，让面试官知道你有框架。
2. **再讲机制**：底层原理/关键步骤，控制在 3-5 句。
3. **给取舍**：代价、边界、适用场景，体现架构思维。
4. **补证据**：线上现象、命令、监控指标，证明你做过。
5. **收边界**：什么情况下不适用，避免过度承诺。

常见扣分：只背结论不讲机制；一上来讲细节没有框架；把「八股」答成教科书，不结合业务；遇到追问就改口。

## 小结

- 面经是**题型样本**，不是考纲；公司风格差异主要在追问深度与项目占比。
- Java 基础高频是 HashMap/并发/线程池/ThreadLocal；JVM 高频是 GC 排查与类加载；MySQL 高频是索引、MVCC、隔离级别；Redis 高频是锁、缓存三问题、一致性。
- 场景题的高分点不是「方案多」，而是**能算容量、说清取舍、给兜底与对账**。
- 答题用「结论 → 机制 → 取舍 → 证据 → 边界」五步，避免背模板。
- 项目题永远最重要：技术题决定下限，项目深度决定上限。
