# 喜茶 31 题详解：门店、订单与高并发

> 定位：喜茶 Java 后端二面 31 题逐题深答。每题按“面试官想听 → 具体方案 → 可讲的亮点 → 追问”写，目标是把“用过”讲成“做过、踩过坑、有数据”。数字是示例口径，面试时替换成你的真实值；没做过就讲推演，不编经历。

## 一、自我介绍 + 项目

**面试官想听**：你有没有在“门店多、订单峰值高、库存/券/会员强相关”的链路里真正做过决策。别背简历，讲一个能追问 10 分钟的项目。

**答法**：背景给规模：门店数、日订单、峰值 QPS、库存/券的量级；目标给指标：下单 P99、超卖率、缓存命中率、故障恢复时间；动作只讲 2–3 个关键决策，例如“库存按门店+SKU+时段预占”“菜单三级缓存”“订单按用户分片”；结果给前后对比；反思讲边界，例如“分片后门店维度查询改用异构表”。

**亮点**：不要讲“用了 Redis/RocketMQ”，讲“为什么不用另一个”。例如“秒杀没用分布式锁，因为锁等待把 P99 拉到 300ms，改用 Lua 后降到 80ms”。

**追问**：你负责哪一段？最难的一次故障是什么？如果重做会改什么？答不上细节就换一个你真做过的项目。

## 二、秒杀特惠饮品，怎么防超卖

**面试官想听**：库存粒度、原子扣减、限购、未支付释放、Redis 与 DB 不一致怎么办。

**方案**：

1. 库存按 `store:sku:slot` 预热到 Redis，活动库存和门店日常库存分开，避免大 key。
2. Lua 原子执行“查库存、查用户限购、扣库存、标记用户”，一次 RTT；扣减用 `stock >= n`。
3. 成功发 MQ 异步创单；订单表 `(user_id, activity_id, sku_id)` 唯一索引；DB 库存条件更新兜底。
4. 未支付 15 分钟延迟消息取消，释放 Redis + DB；日终对账。

**亮点**：秒杀不是“把库存放 Redis 就完了”，要讲清“Redis 扣成功、订单创失败”的回补：消息带预占单号，消费失败回补并告警。示例：峰值 8 万 QPS，超卖 0，Redis 故障时自动停售而不是打穿 DB。

**追问**：为什么不用分布式锁？锁等待/续期把尾延迟拉高；Lua 短临界区更合适。Redis 主从丢数据？DB 条件更新 + 唯一索引兜底。超卖怎么发现？对账“可售 = 总库存 - 已售 - 有效预占”。

## 三、订单创建 MySQL 5000 QPS 怎么优化

**面试官想听**：你先定位还是直接分库分表；知不知道为什么 5000 QPS 会打爆。

**方案**：

1. 先看连接池、慢查询、行锁等待、事务大小、磁盘 fsync；5000 QPS 写 MySQL 常见瓶颈是热点行和事务内 RPC。
2. 缩短事务：事务内不做 RPC/日志；批量插入/合并小事务；更新按主键，避免无索引更新。
3. 热点库存 Redis 预扣；非核心写异步化；订单按用户/门店分片。
4. 连接池按 DB 承载调，压测验证；不要盲目加连接。

**亮点**：先做“写路径拆解”：一条订单写几次 DB、几次 Redis、几次 MQ，合并后从 6 次降到 3 次；示例：P99 从 220ms 降到 90ms。另一个亮点是热点行用“排队 + 分片库存”，不是单纯加机器。

**追问**：分库分表能解决热点单行吗？不能；热点要单独设计。跨分片查询怎么办？异构表/ES。事务太大？拆成业务补偿。

## 四、热点数据问题（新品上线菜单 QPS 暴增）

**面试官想听**：菜单读多写少、按门店热点；你知不知道缓存击穿/热 key，而不是只会加 Redis。

**方案**：

1. Caffeine 本地 + Redis + MySQL；本地 TTL 5–30 秒，Redis TTL 更长；TTL 加随机。
2. 热点 key 失效用互斥重建/逻辑过期；本地缓存挡主流。
3. 变更“更新 DB → 删 Redis → MQ 广播删本地”；版本号兜底。
4. 价格/售罄下单时服务端再校验，展示缓存不承担交易真相。

**亮点**：把菜单拆成“展示字段”和“交易字段”：展示可缓存，价格/库存下单回源；示例：菜单 QPS 10 万，DB 只承受几百。另一个亮点是本地缓存短 TTL + 事件失效，事件丢失也能 30 秒内收敛。

**追问**：逻辑过期返回旧数据能接受吗？菜单展示可以，价格不行。缓存穿透？空值/布隆。Redis 热 key？本地挡 + 分片。

## 五、分布式 ID：门店 + 日期 + 序列号

**面试官想听**：可读、趋势递增、唯一、分片友好，以及高并发怎么取号。

**方案**：

1. 格式 `storeId(4) + yyyyMMdd(8) + seq(6–8)`；seq 用 Redis INCR，按 `store:date` 分 key，每日重置。
2. 高并发用号段模式，一次取 1000 个，减少 Redis 往返；或用雪花 ID 做全局唯一。
3. DB 唯一索引兜底；返回前端用字符串，避免精度丢失。
4. 监控跨天重置、时钟回拨、号段耗尽。

**亮点**：订单号带门店和日期，客服/运营一眼能定位，分库分表按门店也方便；示例：取号 RT 从 2ms 降到 0.2ms（号段）。另一个亮点是号段用完后异步预取，避免请求时等待。

**追问**：为什么不用 UUID？无序、太长、索引不友好。Redis 挂了？切号段/雪花。跨天重复？日期+门店+seq 唯一，DB 兜底。

## 六、JVM 调优实战：G1 日志 + MAT 定位对象泄漏

**面试官想听**：你怎么判断泄漏还是峰值，怎么拿证据，怎么止血。

**方案**：

1. `jstat -gcutil` 看老年代回收后是否回落；G1 日志看 Mixed GC、Humongous、停顿。
2. `jcmd GC.heap_dump`，MAT 看支配树、GC Roots、大对象、线程栈。
3. 常见根因：本地缓存无上限、批量查询、ThreadLocal、大 JSON、连接未关。
4. 先摘流/扩容/重启止血，再改代码；参数最后调，压测验证。

**亮点**：先看“回收后回落”再决定查泄漏还是扩容；示例：定位到本地缓存无上限，FullGC 从每天 12 次降到 1 次。另一个亮点是保留 dump 和 GC 日志，复盘能证明根因，不是“重启好了”。

**追问**：G1 Humongous 怎么产生？大对象超过 Region 一半。dump 影响服务？低峰/摘流。ZGC 适合吗？大堆低延迟可以，但吞吐/成本要权衡。

## 七、跨门店库存同步

**面试官想听**：线上点单和门店 POS 都要扣库存，怎么不超卖、不各扣各的。

**方案**：

1. 中心库存 + 门店库存；下单预占，支付/制作确认，超时释放。
2. 变更发 MQ，各端按版本号更新；门店 POS 离线本地记账，恢复后对账。
3. 允许少量 buffer 防超卖；售罄实时同步；跨店取餐单独库存池。
4. 日终/班次对账，差异工单。

**亮点**：把库存拆成“可售/预占/锁定/已售”，每步有状态和超时；示例：超卖率从 0.8% 降到 0.05%。另一个亮点是门店离线不阻断营业，恢复后按流水对账，而不是强依赖中心。

**追问**：强一致还是最终一致？下单预占要强，展示可最终一致。MQ 重复？幂等。门店改库存？版本号/最后写入。

## 八、分布式锁选型：Redis vs ZooKeeper

**面试官想听**：锁不是保证绝对正确，最终要靠 DB；选型看一致性、性能、运维。

**方案**：

- Redis：`SET NX EX` + Lua 解锁，性能高；问题：超时、主从丢锁、续期。
- ZooKeeper：临时顺序节点，强一致、公平；性能和运维成本高。
- 资金/库存用 DB 条件更新/唯一约束兜底；锁只做减压。
- 关键操作用 fencing token，防旧锁持有者写入。

**亮点**：不要只说“Redis 快”，要讲“Redis 锁超时后，DB 条件更新仍能防重复”；示例：锁超时导致重复请求，DB 唯一键挡住，没有资损。另一个亮点是锁粒度按业务键，不做全局锁。

**追问**：Redlock 能用吗？有争议；强一致用 DB/共识系统。锁续期？watchdog，但别让业务无限持锁。ZK 会话断开？临时节点释放。

## 九、订单状态机设计

**面试官想听**：状态不能乱跳，支付/制作/退款是不同子状态；你怎么防重复。

**方案**：

1. 枚举 + 允许迁移表；变更用 `update ... where status = ?` CAS。
2. 状态变更发事件，库存/支付/通知各自消费；消费幂等。
3. 超时取消、支付回调、退款独立状态，不塞进一个字段。
4. 对账：订单状态与支付/库存一致。

**亮点**：把“状态机”做成“可审计的迁移日志”，每次变更记前后状态、操作人、原因；示例：重复制作投诉下降 60%。另一个亮点是支付回调按状态 CAS，已支付直接返回，不重复发货。

**追问**：为什么不用一个 status？支付、制作、退款语义不同。迁移失败？重读再决策。人工修正？留审计。

## 十、分库分表：按用户 ID 分库后，怎么查某门店所有订单

**面试官想听**：分片键与查询维度不一致时，你怎么避免全分片扫描。

**方案**：

1. 主库按用户 ID 分片；门店维度建异构表/宽表/ES，binlog/CDC 同步。
2. 门店查询走异构层，分页/聚合在异构层做；强实时双写。
3. 年度统计走离线数仓/汇总表。
4. 对账：主库与异构层条数/金额一致。

**亮点**：不追求“一个分片键支持所有查询”，而是“交易按用户、查询按门店异构”；示例：门店订单查询从 8 秒降到 200ms。另一个亮点是异构层可重建，出问题不影响主交易。

**追问**：为什么不用全局二级索引？成本/一致性/运维复杂。同步延迟？提示“稍后”。跨维度聚合？离线/ES。

## 十一、分布式事务：用券下单后扣积分

**面试官想听**：跨服务一致性怎么选型，幂等和补偿怎么做。

**方案**：

1. 下单本地事务：订单 + 券核销 + 本地消息表；消息投递扣积分。
2. 积分服务幂等消费；失败重试/死信；对账补偿。
3. 强约束用 TCC 预扣；一般最终一致足够。
4. 券/积分唯一业务键，防重复。

**亮点**：不是所有场景都上 TCC；用券+积分用本地消息表，简单可靠；示例：掉单率从 0.3% 降到 0.01%。另一个亮点是补偿也幂等，重复补偿不会多扣。

**追问**：为什么不用 2PC？同步阻塞/协调者单点。消息丢失？本地消息表扫描重投。积分扣失败？回滚券/取消订单。

## 十二、MySQL 索引：status=1 AND store_id=100 慢

**面试官想听**：联合索引顺序、回表、低基数状态列怎么放。

**方案**：

1. 建 `(store_id, status, create_time)`：store_id 过滤性强放前，status 次之，时间用于排序/范围。
2. 查询只取必要列，争取覆盖索引；避免 `select *`。
3. `explain` 看 type/rows/Extra；避免函数、隐式转换、前导模糊。
4. 数据量大按时间分区/归档。

**亮点**：不是“加索引”就完，要看 `rows` 和回表；示例：扫描行从 80 万降到 200，P99 从 1.2s 降到 30ms。另一个亮点是低基数 status 不单独建索引，放联合索引后段。

**追问**：联合索引顺序能换吗？看过滤性和最左匹配。索引失效？函数/隐式转换/OR。索引太多？写入成本/空间。

## 十三、Redis 大 Key：500MB 的热门饮品排行榜 ZSET

**面试官想听**：大 key 的阻塞、集群倾斜、拆分和删除。

**方案**：

1. 按区域/品类/时间窗拆 ZSET，例如 `rank:store:date`。
2. 只保留 TopN，历史落 DB/ES；定期 `ZREMRANGEBYRANK` 裁剪。
3. 查询分页 `ZREVRANGE`，不取全量；迁移用 SCAN + 批量。
4. 删除用 `UNLINK` 异步，避免阻塞主线程。

**亮点**：把“一个 500MB 榜单”拆成“每店每天 Top100”，内存和删除都可控；示例：删除耗时从 2 秒降到 20ms。另一个亮点是榜单可重建，Redis 丢了从 DB/ES 回填。

**追问**：为什么不能 DEL？大 key 删除阻塞。热 key？本地缓存 + 分片。数据一致性？榜单允许短延迟。

## 十四、缓存一致性：更新饮品价格，先更新 DB 还是先删缓存

**面试官想听**：你知道双写不原子，目标是最终一致；价格以下单校验为准。

**方案**：

1. Cache Aside：先更新 DB，再删缓存；读未命中回填。
2. 删失败 MQ/binlog 补偿；延迟双删降低并发脏读。
3. 缓存带版本号；价格结算服务端回源。
4. 监控缓存与 DB 差异。

**亮点**：价格这类交易字段不信任缓存，展示缓存、下单回源；示例：价格错单从每月 10 单降到 0。另一个亮点是删除失败有补偿，不靠“下次读”碰运气。

**追问**：先删缓存再更新 DB 行不行？并发读回填旧值。延迟双删要延迟多久？按读耗时/主从延迟。缓存雪崩？随机 TTL。

## 十五、1 亿订单历史表，怎么优化“我的订单”深分页

**面试官想听**：offset 为什么慢，游标/ES/归档怎么选。

**方案**：

1. 游标：按 `create_time/id` 递减，`where create_time < last`，每页取 N。
2. 限制最大页；提供时间/状态筛选缩小范围。
3. 复杂搜索走 ES，`search_after` 分页。
4. 冷数据归档，热表只留近期。

**亮点**：把“跳页”改成“时间锚点 + 下拉加载”，既快又符合用户习惯；示例：深分页 P99 从 3s 降到 80ms。另一个亮点是 ES 与 DB 对账，避免搜到已删除订单。

**追问**：为什么不用 limit offset？偏移越大越慢，数据变化会重复/漏。用户要跳第 100 页？限制/时间筛选。ES 延迟？提示/以 DB 为准。

## 十六、Elasticsearch 实现“附近门店”

**面试官想听**：geo_point、距离过滤、排序、分页、数据同步。

**方案**：

1. 门店索引 `geo_point`；`geo_distance` 过滤半径，按距离/评分排序。
2. 分页 `search_after`，返回距离；热门区域缓存。
3. 门店变更 binlog/CDC 同步；坐标纠偏/围栏服务端处理。
4. 对账/重建索引。

**亮点**：不只按距离，还叠加“营业中/库存/评分”，否则最近的门店可能没货；示例：附近门店点击转化提升 12%。另一个亮点是 ES 不可用降级 Redis GEO/DB 范围查询。

**追问**：geo_distance 和 geohash 怎么选？ES 适合多条件排序。深分页？search_after。数据延迟？提示/降级。

## 十七、消息队列选型：Kafka 和 RocketMQ 在订单通知场景

**面试官想听**：可靠、延迟、事务、顺序、运维，不是只看吞吐。

**方案**：

- Kafka：高吞吐、分区顺序、生态好；延迟/事务消息弱，适合日志/流。
- RocketMQ：事务消息、延迟消息、顺序消息、死信，Java 生态友好，适合订单通知。
- RabbitMQ：路由灵活、低延迟，吞吐较低。

**亮点**：订单通知选 RocketMQ，不是因为它“快”，而是延迟/事务/死信更贴合；示例：延迟取消用原生延迟消息，少一套调度系统。另一个亮点是无论选哪个，消费幂等 + 对账不能少。

**追问**：Kafka 能做延迟吗？外挂调度，不如 RocketMQ 原生。怎么防丢？acks=all + 重试 + 本地消息表。怎么防重？业务键幂等。

## 十八、订单 30 分钟未支付自动取消

**面试官想听**：千万级订单不能全表轮询；延迟触发、幂等、库存回补。

**方案**：

1. 下单写延迟消息/时间轮/Redis ZSet，到期检查状态。
2. 未支付取消、释放库存/券；取消幂等。
3. 分片扫描兜底；重复触发按状态 CAS。
4. 监控延迟与取消成功率。

**亮点**：延迟消息只做“触发”，最终以订单状态为准，避免消息乱序误取消；示例：取消成功率 99.9%，库存回补差异 0。另一个亮点是取消和支付并发用 CAS，谁先成功谁算。

**追问**：为什么不用每分钟扫表？数据量大、命中率低。消息丢了？扫描补偿。取消后用户又支付？支付回调检查状态，退款/恢复。

## 十九、促销导致 MQ 积压 10 万条，怎么快速消费

**面试官想听**：先看瓶颈在消费者、分区、下游还是消息体；不要盲目加线程。

**方案**：

1. 看堆积量、消费 TPS、分区数、消费者数、下游 RT。
2. 加消费者/线程、扩分区、批量消费；下游慢先优化/降级。
3. 非核心消息可降级/丢弃（业务确认）；核心消息保顺序。
4. 防把下游打垮，限流保护；恢复后回放。

**亮点**：先判断“能不能丢”，再决定扩容还是降级；示例：推荐类消息降级 40%，核心订单消息零丢失。另一个亮点是积压时先扩分区再扩消费者，否则消费者空闲。

**追问**：能清空队列吗？核心不能。顺序怎么保？按 key 分区。重复消费？幂等。

## 二十、Dubbo 接口响应时间波动大，怎么定位网络还是服务端

**面试官想听**：全链路拆解：客户端、网络、服务端、下游、GC。

**方案**：

1. TraceId 串客户端/服务端；看耗时在哪个段。
2. 服务端看 P99、线程池队列、GC、锁、下游 RT；客户端看连接池、超时、重试。
3. 网络看丢包、带宽、跨机房延迟；对比同机房。
4. 治理：超时/重试/隔离/限流；固定容量压测。

**亮点**：平均 RT 正常不代表没问题，要看 P99 和线程池排队；示例：定位到某接口重试放大，关重试后 P99 从 800ms 降到 120ms。另一个亮点是跨机房调用单独监控，不混在同城指标里。

**追问**：重试怎么防放大？预算/熔断/只重试幂等。线程池满？隔离/限流。网络抖动？多机房/超时。

## 二十一、分布式配置中心：动态调整每门店最大并发订单数

**面试官想听**：实时生效、灰度、回滚、审计、配置中心故障兜底。

**方案**：

1. Nacos/Apollo 按门店 key 配置；客户端监听 + 本地缓存。
2. 灰度按门店/比例；保留旧值回滚；审计操作人。
3. 非法值/上限保护；本地快照防配置中心故障。
4. 监控拒绝率/排队。

**亮点**：配置不是“改个值”，要有边界和回滚；示例：某门店误配 10 倍并发，上限保护挡住，未打爆 DB。另一个亮点是按门店灰度，先 5 家再全量。

**追问**：为什么不用 DB 配置表？缺推送/灰度/审计。配置中心挂了？读本地。配置冲突？优先级/版本。

## 二十二、会员成长体系：积分 + 等级

**面试官想听**：积分是流水，等级是规则计算；不能直接改余额。

**方案**：

1. 积分流水为事实源，余额派生/缓存；业务键幂等。
2. 等级规则版本化（成长值/消费/任务），异步计算；变更发事件。
3. 防刷：频次、行为、黑名单；积分有效期/扣减规则。
4. 对账：流水汇总 = 余额；等级与成长值一致。

**亮点**：等级不是每次实时算，而是“事件驱动 + 准实时”，避免大促时全量算；示例：等级更新延迟从小时级降到分钟级。另一个亮点是积分流水可追溯，客服能查每一笔来源。

**追问**：等级实时还是离线？看权益时效。积分过期？定时任务 + 流水。刷分？风控/上限。

## 二十三、实时销量排行榜：每 5 分钟更新区域 Top10

**面试官想听**：流式聚合、窗口、退款回冲、榜单存储。

**方案**：

1. 订单事件 → Flink 按区域/品类开窗统计。
2. 结果写 Redis ZSet；5 分钟刷新；只保留 TopN。
3. 退款/取消回冲；历史归档。
4. 监控延迟与一致性。

**亮点**：榜单允许近似，但要能解释“为什么某店第一”；示例：大促期间榜单延迟 <10 秒。另一个亮点是退款回冲用负值事件，避免榜单虚高。

**追问**：为什么不查 DB？聚合慢/压力大。流任务失败？checkpoint/重跑。刷单？风控过滤。

## 二十四、优惠券核销：防止同一张券多门店并发使用

**面试官想听**：券状态机、DB 条件更新、Redis 占位、幂等。

**方案**：

1. 券状态：未使用→锁定→已使用/释放；DB `where status=UNUSED`。
2. Redis 原子占位；核销幂等键 `(coupon_id, order_id)`。
3. 门店/订单绑定；失败释放；超时回滚。
4. 对账：券记录与订单/支付一致。

**亮点**：只靠 Redis 不行，主从切换会重复；DB 条件更新是最后防线。示例：并发核销 0 重复。另一个亮点是核销失败自动释放，不让券卡死。

**追问**：重复核销？幂等键拒绝。Redis 与 DB 不一致？以 DB 为准。券跨店？规则限制。

## 二十五、门店智能调度：按订单量和制作时长分配制作人员

**面试官想听**：产能模型、优先级、负载均衡、超时预警。

**方案**：

1. 订单入队，按取餐时间/优先级排序；制作时长按品类/数量估算。
2. 产能：每人当前任务数、设备能力、班次；负载均衡分配。
3. 动态排班/借调；超时预警；完成率复盘。
4. 指标：出餐时长、超时率、人均产出。

**亮点**：不是简单轮询，按“技能 + 当前负载 + 取餐时间”分配；示例：超时率从 12% 降到 5%。另一个亮点是把制作时长做成可学习参数，按门店/品类校准。

**追问**：突发订单？溢出到其他门店/延迟取餐。人员缺勤？重排。系统故障？手工派单。

## 二十六、多级缓存：Caffeine + Redis + MySQL 一致性

**面试官想听**：本地缓存失效最难；变更广播、版本、短 TTL。

**方案**：

1. 读本地→Redis→DB，回填；本地 TTL 短。
2. 写 DB→删 Redis→MQ 广播删本地。
3. 版本号防旧值覆盖；关键字段下单回源。
4. 监控命中率/不一致。

**亮点**：本地缓存不是“加了就快”，要有失效通道；示例：菜单读取 P99 从 80ms 降到 8ms。另一个亮点是 MQ 丢失靠短 TTL 收敛，不长期脏读。

**追问**：能不能不删本地？多实例会脏读。雪崩？随机 TTL。Redis 挂了？降级 DB + 限流。

## 二十七、手写线程安全计数器，比较 synchronized、ReentrantLock、LongAdder

**面试官想听**：竞争程度、一致性要求、读多写少。

**方案**：

- `synchronized`：简单，低竞争够用；高竞争排队。
- `ReentrantLock`：可中断/超时/公平，适合需要控制。
- `LongAdder`：分段累加，高并发写吞吐最好；读汇总，弱一致。
- `AtomicLong`：CAS，竞争高自旋。

**亮点**：计数允许弱一致就用 LongAdder，不要为了“精确”上锁；示例：点赞计数 QPS 从 5 万提到 20 万。另一个亮点是读多写少用 LongAdder + 定时快照。

**追问**：LongAdder 为什么快？Cell 分散 CAS。sum 是原子快照吗？不是。什么时候用锁？资金/强一致。

## 二十八、CompletableFuture 编排“订单 + 库存 + 优惠”

**面试官想听**：并行、线程池隔离、超时、异常降级。

**方案**：

1. 每个下游独立线程池，避免公共 ForkJoinPool 阻塞。
2. `supplyAsync` 并行，`thenCombine` 聚合；`orTimeout` 超时。
3. `exceptionally/handle` 降级；结果一致性校验。
4. 链路埋点看各段耗时。

**亮点**：并行不是“越多越快”，线程池隔离防雪崩；示例：接口 RT 从 300ms 降到 120ms。另一个亮点是超时预算按下游分配，不让一个慢调用拖死全链路。

**追问**：为什么不用公共池？阻塞影响全局。某段失败？默认值/降级。线程池满？隔离/限流。

## 二十九、ThreadLocal 内存泄漏

**面试官想听**：ThreadLocalMap 的 key 弱引用、value 强引用；线程池长存活。

**方案**：

1. `set` 以 ThreadLocal 为 key；`remove` 清 Entry。
2. 线程池使用必须 `finally remove`；不存大对象/用户上下文。
3. 异步传递用 TransmittableThreadLocal，但也要清理。
4. 监控 ThreadLocalMap 大小。

**亮点**：泄漏不是“ThreadLocal 的锅”，是线程池没清理；示例：一次导出功能导致老年代涨 2G，定位到 ThreadLocal 存了大 List。另一个亮点是代码扫描 + Code Review 卡点。

**追问**：key 为什么弱引用？让 ThreadLocal 可回收。remove 一定要吗？线程池必须。异步传递？TTL/显式参数。

## 三十、线上 synchronized 竞争导致性能下降，怎么优化

**面试官想听**：先确认锁竞争，再缩小临界区/分段/无锁。

**方案**：

1. 看线程 BLOCKED、锁持有时间、GC/DB 排除。
2. 缩小临界区，锁内不做 RPC/IO/日志。
3. 锁分段/按 key 锁；读写锁；CAS/LongAdder。
4. 压测验证吞吐/P99。

**亮点**：把一把大锁拆成 64 段，按用户 hash 选段；示例：吞吐从 2 万提到 8 万。另一个亮点是锁内只做内存操作，DB/RPC 移到锁外。

**追问**：锁粗化/消除？JIT 有限，业务仍要短。公平锁？高并发下吞吐低。死锁？按顺序加锁/超时。

## 三十一、8G 内存订单服务的 G1 参数模板

**面试官想听**：参数是起点，要按压测/对象分配调；知道 G1 的关键参数。

**方案**：

```text
-Xms8g -Xmx8g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:InitiatingHeapOccupancyPercent=45
-XX:+HeapDumpOnOutOfMemoryError
-Xlog:gc*:file=gc.log:time,uptime,level,tags
```

年轻代/Region 用默认，观察 Humongous；Metaspace 设上限；容器注意 CPU/内存感知。

**亮点**：不硬设 `Xmn`，让 G1 动态调年轻代；示例：P99 从 180ms 降到 90ms。另一个亮点是 GC 日志进监控，停顿/频率异常告警。

**追问**：为什么不设 Xmn？G1 动态调整，硬设可能适得其反。ZGC？大堆低延迟，但吞吐/成本权衡。OOM 怎么查？dump + MAT。

## 小结

- 喜茶 31 题的核心是“库存/秒杀、缓存、订单状态、分库分表、JVM/并发”。
- 每题都要落到“具体链路 + 数据模型 + 失败兜底 + 指标”，亮点用数字和取舍证明。
- 不要把“用了某个中间件”当亮点，要讲“为什么不用另一个”。
