# 蚂蚁 18 题详解：支付、一致性、高并发

> 定位：蚂蚁支付后端 18 题逐题深答。每题按“面试官想听 → 具体方案 → 关键取舍 → 可讲的亮点 → 追问”写，重点讲资金正确性、最终一致、故障兜底与对账。数字是示例口径，面试时替换成你的真实值；没做过就讲推演，不编经历。

## 一、自我介绍 + 项目

**面试官想听**：你在资金流的哪一段做过决策；出过资损/故障没有；对账、幂等、补偿是不是你亲手做的。

**答法**：背景给交易量、峰值 TPS、支付渠道数、账务/风控规模；目标给成功率、P99、资损率、对账差异率；动作讲 2–3 个关键设计，例如“本地消息表 + 幂等键”“TCC 空回滚/悬挂处理”“日终三方可对账”；结果给前后对比；反思讲边界与下一次改进。

**关键取舍**：不要把所有系统都说成自己主导；选一个你真负责的模块，讲透“为什么这么设计、哪里会坏、怎么发现”。

**亮点**：不要只说“高并发”，要说“支付回调重复导致重复入账，我用业务键 + 状态机把重复入账降到 0”；数字和故障比框架名更有说服力。

**追问**：你负责支付、账务还是风控？最惊险的一次故障？如果重做会改什么？答不上就换项目。

## 二、TCC 场景下支付重复回调怎么处理

**面试官想听**：TCC 的 Confirm/Cancel 会重复、乱序、超时；你知不知道空回滚和悬挂。

**方案**：

1. 幂等键 `(globalTxId, branchId)`，DB 唯一索引；重复 Confirm 直接返回成功。
2. 状态机 `TRYING → CONFIRMED/CANCELLED`；Confirm 只能从 TRYING 迁移，用 CAS。
3. 空回滚：Cancel 先到、Try 未到，记录“空回滚标记”；后续 Try 看到标记直接拒绝，避免“悬挂”。
4. Confirm/Cancel 失败重试 + 死信 + 人工；日终对账。

**关键取舍**：TCC 适合强一致/资源预占，不适合所有场景；一般异步用本地消息表更简单。Confirm 重试必须幂等，不能“再扣一次”。

**亮点**：不只处理“重复”，还处理“空回滚/悬挂”这两个 TCC 真坑；示例：重复回调 1 万次，零重复入账。另一个亮点是 Confirm 前先查 Try 记录，避免“没 Try 就 Confirm”。

**追问**：Confirm 超时？查询 + 补偿，不盲目重试。Cancel 失败？挂账人工。TCC 与 Saga 区别？TCC 资源预占，Saga 长流程补偿。

## 三、接口限流与熔断怎么设计

**面试官想听**：限流和熔断的区别、阈值怎么定、组件故障怎么兜底。

**方案**：

1. 网关/服务多级限流：令牌桶/滑动窗口；按 IP、用户、接口、租户维度。
2. 集群限流 Redis/Lua 或 Sentinel；本地令牌桶兜底，防 Redis 故障全局限流失效。
3. 熔断看错误率/RT/慢调用比例，半开探测恢复；按依赖隔离。
4. 被限流返回 429/重试时间；核心接口预留配额。

**关键取舍**：限流保自己，熔断保下游；阈值来自压测 + 容量评估，不是拍脑袋。本地限流只做兜底，不能替代全局配额。

**亮点**：大促前压测发现 DB 只能扛 1.2 万 TPS，网关限流设 1 万，留 20% buffer；示例：峰值 1.5 万时核心接口不崩，非核心 429。另一个亮点是熔断后走缓存/默认值，不让一个下游拖死全站。

**追问**：限流组件挂了？本地兜底。阈值调了不生效？配置中心/灰度。重试风暴？退避 + 预算。

## 四、缓存与数据库一致性怎么保证

**面试官想听**：你知道强一致做不到，目标是最终一致、不长期脏读；资金不信任缓存。

**方案**：

1. Cache Aside：读未命中回填；写先更新 DB 再删缓存。
2. 删失败 MQ/binlog 补偿；延迟双删降低并发脏读窗口。
3. 缓存带版本号/逻辑过期；热点 key 互斥重建。
4. 资金/库存关键操作落库校验，不信任缓存。

**关键取舍**：先删缓存再更新 DB 容易被并发读回填旧值；延迟双删只能降低窗口，不能消灭。交易字段必须回源。

**亮点**：把缓存分为“展示缓存”和“交易缓存”，交易字段下单回源；示例：余额展示延迟 1 秒可接受，支付校验 0 误差。另一个亮点是删除失败有补偿任务，不靠“下次读”。

**追问**：延迟双删延迟多久？按读耗时/主从延迟。缓存击穿？互斥/逻辑过期。主从延迟？读主库/版本号。

## 五、Flink 实时大屏：成交额统计

**面试官想听**：事件时间、窗口、乱序、Exactly-Once、退款回冲。

**方案**：

1. 支付成功事件进 Kafka，按事件时间开窗（1s/1min），Watermark 处理乱序。
2. KeyBy 业务线/地区，聚合 GMV/笔数；退款用负值或单独流扣除。
3. 结果写 Redis/OLAP，大屏查询；Checkpoint 保证恢复。
4. 维表用广播状态/Async I/O；监控延迟与位点。

**关键取舍**：大屏允许近似，但退款必须回冲，否则 GMV 虚高；迟到数据要侧输出校正，不能无限等。

**亮点**：大屏延迟 <3 秒，退款回冲 T+0；示例：大促 GMV 与离线对账差异 <0.1%。另一个亮点是 Checkpoint + 幂等 sink，故障恢复不重复写。

**追问**：为什么不用 DB 聚合？高吞吐压垮 DB。Flink 失败？checkpoint 恢复。重复计算？幂等 sink/对账。

## 六、分布式锁在支付场景怎么用

**面试官想听**：锁不是资金正确性的最后防线；DB 唯一约束/状态机才是。

**方案**：

1. `SET key value NX EX`，value 唯一请求 ID；解锁 Lua 比对 value。
2. 锁超时短于事务；长任务续期；关键操作用 fencing token。
3. 账务用 `(biz_id, account_id)` 唯一流水 + 条件更新；重复请求幂等。
4. 锁失败快速失败/排队，不无限等待。

**关键取舍**：Redis 主从切换可能丢锁，所以锁只能减少并发，不能保证唯一；最终靠 DB 唯一键/状态 CAS。

**亮点**：锁超时导致重复请求，DB 唯一键挡住，没有资损；示例：Redis 主从切换丢锁，账务仍正确。另一个亮点是 fencing token 防旧锁持有者写入。

**追问**：Redlock 能解决主从丢锁吗？有争议；强一致用 DB/共识。锁续期？watchdog，但别无限持锁。死锁？TTL + 顺序加锁。

## 七、消息可靠：支付成功通知商户

**面试官想听**：本地事务与发消息不原子；本地消息表/事务消息、重试、幂等、对账。

**方案**：

1. 支付落库与本地消息表同事务；投递 MQ，通知服务发送。
2. 商户回调失败指数退避、死信、人工；商户侧 `request_id` 幂等。
3. 回调验签、防重放；失败可主动查询。
4. 对账：支付流水、通知记录、商户回执。

**关键取舍**：通知是“至少一次”，不是“恰好一次”；端到端靠商户幂等 + 对账，不能只靠 MQ。

**亮点**：通知成功率 99.99%，重复通知商户可幂等；示例：掉单从每月 20 笔降到 0。另一个亮点是回调失败转主动查询，避免只靠重试。

**追问**：为什么不用 2PC？阻塞/单点。消息丢失？本地消息表扫描。长期失败？人工工单。

## 八、库存预占：下单锁库存、超时释放

**面试官想听**：预占与实扣分离、防超卖、重复释放、对账。

**方案**：

1. Redis Lua 原子预占，记录预占单号；DB `stock = stock - n where stock >= n` 兜底。
2. 预占状态 `HELD → CONFIRMED/RELEASED`；支付确认，超时释放。
3. 延迟消息释放；重复释放幂等；预占与订单绑定。
4. 对账：可售 = 总库存 - 已确认 - 有效预占。

**关键取舍**：预占不是“锁死库存”，要有超时和释放；预占与实扣分开，避免长期占用。

**亮点**：大促超卖 0，库存利用率提升 15%；示例：Redis 挂了读 DB/限流，不让预占穿透。另一个亮点是预占单号贯穿订单/支付/释放，能对账。

**追问**：释放失败？重试 + 对账。超卖？DB 条件更新 + 唯一约束。预占过期又支付？检查状态，恢复/退款。

## 九、接口从 400ms 优化到 80ms

**面试官想听**：先分解耗时，再优化；不是直接换框架/加机器。

**方案**：

1. 埋点拆 DB、RPC、序列化、GC、排队各占多少。
2. 合并查询/批量接口；串行改并行，隔离线程池 + 超时。
3. 加缓存、优化索引/SQL、限制返回字段；异步非核心。
4. 压测回归，防优化引入不一致。

**关键取舍**：最大收益往往不是“换框架”，而是“少调一次 RPC/少查一次 DB”；并行要有超时预算，否则尾延迟更差。

**亮点**：6 次 RPC 合并为 2 次，RT 从 400ms 降到 80ms；示例：P99 从 600ms 降到 120ms。另一个亮点是并行线程池按下游隔离，慢下游不拖累其他接口。

**追问**：为什么优化后 P99 还高？排队/GC/热点。线程池怎么隔离？按下游。缓存一致性？交易字段回源。

## 十、会话管理：分布式 Session

**面试官想听**：多实例共享、过期、注销、踢下线、防劫持。

**方案**：

1. Token/Session ID 存 Redis，带用户、设备、过期；Cookie 只存 ID。
2. 请求校验并续期；注销删除；异地登录踢下线。
3. 敏感操作二次校验；Token 签名/加密；防 CSRF。
4. Redis 故障降级/重登；会话不存大对象。

**关键取舍**：JWT 无状态但难踢下线/续期；服务端 Session 可控性更强。短期 Token + 服务端黑名单是折中。

**亮点**：账号被盗后 1 分钟内全端失效；示例：会话劫持靠设备绑定 + 风险评分挡住。另一个亮点是会话 ID 轮换，防固定攻击。

**追问**：Redis 挂了？重登/本地短缓存。多端登录？设备维度。Token 泄露？强制失效/黑名单。

## 十一、风控 100ms 内完成大量规则

**面试官想听**：规则分级、特征预计算、并行、超时降级。

**方案**：

1. 强规则同步（黑名单、限额），弱规则异步/准实时。
2. 特征离线/近实时预计算，线上只查特征；名单本地缓存。
3. 并行调用 + 总超时预算；规则引擎按优先级短路。
4. 模型异步打分；高风险先拦截后复核；降级策略明确。

**关键取舍**：100ms 不是“所有规则都跑”，而是“强规则同步 + 弱规则异步”；风控挂了不能全放行，也不能全拒。

**亮点**：P99 95ms，拦截率不降；示例：强规则 20 条同步，弱规则 200 条异步。另一个亮点是风控超时按“默认放行/限额/人工”分场景，不搞一刀切。

**追问**：100ms 含网络吗？端到端预算。下游超时？小于总预算。风控挂了？限额/人工。

## 十二、20 万 QPS 限流怎么做

**面试官想听**：集群限流、分片、租户配额、本地兜底、防重试风暴。

**方案**：

1. 网关按接口/租户/用户限流；Redis/Lua 集群计数，分片避免热 key。
2. 服务本地令牌桶兜底；集群限流故障时本地保护。
3. 分级配额：核心保底，非核心可降级；排队/429。
4. 压测 + 动态阈值 + 监控拒绝率。

**关键取舍**：20 万 QPS 不可能单机精确限流，必须“网关集群 + 本地兜底”；但本地限流不能替代全局配额。

**亮点**：大促 25 万 QPS，核心接口通过率 99%，非核心降级 30%；示例：租户配额防单租户打满。另一个亮点是限流返回重试时间，减少客户端盲目重试。

**追问**：为什么不用 Guava RateLimiter？单机不精确。Redis 热 key？分片。重试放大？退避 + 预算。

## 十三、分布式事务补偿怎么做

**面试官想听**：补偿不是“失败了再试”，要有状态、幂等、重试策略、人工兜底。

**方案**：

1. 记录事务状态/步骤，失败进补偿队列；业务键幂等。
2. 指数退避 + 最大次数 + 死信；区分可重试/不可重试。
3. 正向重试与反向冲正/退款；资金类记账。
4. 对账发现差异，人工工单。

**关键取舍**：补偿不能保证一定成功，只能最终一致 + 人工；补偿也要防重复，冲正要有流水。

**亮点**：补偿成功率 99.9%，重复补偿 0；示例：不可重试错误直接转人工，不浪费重试。另一个亮点是补偿分级，自动/人工分明。

**追问**：补偿一定成功吗？不能。怎么防重复？幂等键。补偿失败告警？死信/值班。

## 十四、Canal 同步 MySQL 到 ES/缓存

**面试官想听**：binlog、顺序、重复、延迟、DDL、全量 + 增量。

**方案**：

1. Canal 订阅 binlog，投 MQ 按主键/表分区保序。
2. 消费端幂等 upsert；ES 按主键更新；缓存删除。
3. 全量 + 增量：先全量重建，再切增量；位点监控。
4. DDL/字段变更流程化；对账。

**关键取舍**：Canal 是数据同步，不是业务消息；不能保证端到端 exactly-once，靠幂等 + 对账。

**亮点**：ES 与 DB 差异 <0.01%；示例：全量重建可切换，不怕 mapping 变更。另一个亮点是位点/延迟监控，积压提前告警。

**追问**：乱序？版本号/主键分区。延迟？监控/降级。重复？幂等 upsert。

## 十五、异地多活：支付数据同步

**面试官想听**：单元化、路由、同步、冲突、切换、RTO/RPO。

**方案**：

1. 按用户/商户单元化，请求路由到归属单元；避免跨单元事务。
2. 数据异步/准实时同步；关键流水全局 ID + 对账。
3. 冲突“归属单元为准 + 版本号”；跨单元转账走中心/冲正。
4. 机房故障切流，演练 RTO/RPO。

**关键取舍**：支付多活不能简单双写，必须单元化；跨单元交易走“中心记账 + 冲正”，不搞分布式事务硬扛。

**亮点**：切换 RTO 5 分钟，RPO 0（同城同步）；示例：单元化后跨机房调用下降 90%。另一个亮点是切流演练按真实故障剧本，不只看监控。

**追问**：双活双写行不行？冲突难解。同步延迟？读本地/降级。脑裂？仲裁/预案。

## 十六、SkyWalking 链路追踪怎么落地

**面试官想听**：TraceId 透传、采样、埋点规范、告警、成本。

**方案**：

1. 入口生成/透传 TraceId；跨线程/线程池/MQ 传递。
2. 采样按接口/错误动态调整；核心全采样，低价值低采样。
3. 标注业务维度（租户/订单/门店）；慢调用/错误告警。
4. 存储按天保留，成本控制。

**关键取舍**：链路追踪不是“装 Agent”，而是“埋点规范 + 采样 + 告警”；全量采集成本高，必须分级。

**亮点**：排查一次跨服务超时从 2 小时降到 10 分钟；示例：错误链路全采样、正常低采样，成本降 70%。另一个亮点是 TraceId 跨 MQ 传递，异步链路也能串。

**追问**：Trace 和 Metrics/Logging 区别？单请求/趋势/细节。Agent 故障？异步/降级。TraceId 丢失？网关补。

## 十七、慢查询索引怎么设计

**面试官想听**：过滤性、最左匹配、覆盖索引、写入成本。

**方案**：

1. `explain` 看 type/rows/Extra；联合索引“等值在前、范围在后、排序匹配”。
2. 避免函数/隐式转换/前导模糊；分页游标。
3. 覆盖索引减少回表；长字段前缀/单独表。
4. 清理无用索引；慢查询监控。

**关键取舍**：索引不是越多越好，写入也有成本；低基数 status 不单独建索引，放联合索引后段。

**亮点**：一条联合索引把扫描 80 万行降到 200 行；示例：P99 从 1.2s 降到 30ms。另一个亮点是用 `explain analyze` 验证实际行数，不只看预估。

**追问**：status 放前面吗？通常不。索引失效？函数/转换/OR。分页深？游标/ES。

## 十八、缓存穿透：查不存在的数据

**面试官想听**：空值、布隆、限流、防刷、误判处理。

**方案**：

1. 空值缓存短 TTL + 布隆过滤器；非法 ID 直接拒绝。
2. 接口限流/防刷；参数校验。
3. 热点 key 互斥重建；随机 TTL 防雪崩。
4. 监控穿透率/DB QPS。

**关键取舍**：布隆只能判断“可能存在/一定不存在”，不能删除；数据后来创建要能让空值缓存失效。

**亮点**：恶意查询 QPS 10 万，DB 只看到几百；示例：布隆误判可回源，不直接拒绝。另一个亮点是空值 TTL 短 + 创建时主动删，避免“新数据查不到”。

**追问**：布隆能删除吗？标准不能。空值多久？短 TTL。雪崩？随机 TTL/互斥。

## 小结

- 蚂蚁 18 题的核心是“资金正确性 + 最终一致 + 高并发保护”。
- 支付回调/TCC 要讲幂等键、状态机、空回滚/悬挂、对账；限流熔断要分级、留配额、防重试风暴。
- 缓存不承担资金真相；多活先单元化，别简单双写；链路追踪要控采样与成本。
