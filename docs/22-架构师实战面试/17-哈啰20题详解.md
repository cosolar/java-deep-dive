# 哈啰 20 题详解：出行、换电与调度

> 定位：哈啰后端 20 题逐题深答。每题按“面试官在考什么 → 真实约束 → 方案与数据模型 → 关键取舍 → 可讲的亮点 → 追问”展开，目标是能口述 3–5 分钟，而不是背一句话结论。文中的 QPS、车辆数、SLA、优化比例是示例口径，面试时替换成你的真实数字；没做过就讲推演，不编经历。

## 一、车辆故障上报与 2 小时派单

**面试官在考什么**：不是会不会建工单，而是你能不能把“安全类故障”拆成可运营的 SLA，并处理重复上报、误报、运维造假。

**真实约束**：城市有数百个运营网格、数万辆单车，运维人数有限；故障分安全类（刹车、断电）和普通类（车筐损坏）；2 小时是处理完成目标，不是派单目标；同一辆车可能被多个用户上报。

**方案**：

1. 上报聚合：`bikeNo + faultType + 10 分钟窗口` 做幂等键，重复上报累加次数但不新建工单；安全类直接升 P0。
2. 工单状态机：`REPORTED → SCREENED → DISPATCHED → ACCEPTED → ARRIVED → REPAIRED → CLOSED`，另有 `REJECTED`、`ESCALATED`。每次迁移记时间戳，SLA 拆成“接单 15 分钟、到场 60 分钟、修复 120 分钟”三个子指标。
3. 派单召回：按运营网格取候选运维，过滤休息/超载/技能不匹配；评分 `0.4*距离 + 0.25*当前工单数 + 0.2*历史接单率 + 0.15*SLA 紧急度`，P0 故障额外加权。
4. 计时与升级：RocketMQ 延迟消息在子 SLA 到期时检查状态；未接单扩大半径/加补贴，未到场升级区域主管并改派。

**关键取舍**：为什么不用 Redis ZSet 做延迟？工单量远小于订单，RocketMQ 延迟消息更简单；ZSet 适合海量、可接受轮询的场景。为什么按网格不按全城最近？跨网格派单会让运维在路上耗尽 SLA，且无法考核区域供给。

**可讲的亮点**：把“2 小时”拆成三个子 SLA 分别考核，避免运维只在最后点“完成”造成虚假达标；上线后 P0 超时率从 8% 降到 2%，靠的是子 SLA 预警而不是事后罚。另一个亮点是误报不占 SLA，但累计误报会影响用户信用，减少恶意报修。

**追问**：运维到了发现修不了怎么办？转拖车/回收，工单转 `ESCALATED`，不能直接关单。重复延迟消息？按工单状态 CAS，已关单直接忽略。运维和用户串通虚假上报？照片+定位+车辆蓝牙/锁状态多证据，异常工单抽检。

## 二、单车定点调度

**面试官在考什么**：你有没有把“淤积/短缺”变成可计算的供需缺口，而不是凭经验搬车。

**真实约束**：调度车有容量和班次，跨区要时间；早晚高峰需求变化快；预测错了要有兜底；调度成本要能算 ROI。

**方案**：

1. 以 15–60 分钟为粒度，用历史骑行、天气、节假日、地铁客流、周边活动预测每个网格的借还需求，算 `缺口 = 预测需求 - 可用车辆 - 预计流入`。
2. 缺口分级：`>20 辆` 为严重、`5–20` 为紧张、`<5` 不调度；避免为 1 辆车跨区，调度成本大于收益。
3. 把任务建模成带容量、时间窗、往返成本的 VRP；线上用“贪心插入 + 局部交换”求可用解，每 10 分钟滚动重算，不求全局最优。
4. 下发任务给调度车/运维，记录装车数、里程、完成率、单次成本；按网格复盘“调度后缺口是否真的下降”。

**关键取舍**：全城最优是 NP-hard，且需求实时变；区域次优 + 高频重算更实用。为什么还要人工兜底？大型活动/突发暴雨预测不到，调度主管要能手动插单。

**可讲的亮点**：不是只看“哪里缺车”，而是看“调度后 30 分钟缺口是否闭合”；把调度效果从“搬了多少辆”改成“缺口闭合率”，避免为了 KPI 把车搬到不需要的地方。示例：某商圈早高峰缺口 30 辆，调度后 30 分钟降到 5 辆，单次调度成本 4 元，低于流失 10 单的损失。

**追问**：预测偏差大怎么办？保留 buffer 车辆、人工插单、活动前预投放。调度车故障？任务重派并降级为运维小批量搬运。怎么防止调度车司机虚报？GPS 轨迹 + 装车扫码 + 到达拍照。

## 三、骑行计费异常修正

**面试官在考什么**：计费的可解释、可回放、可退款。用户看到“短距离扣 10 元”，你要能说清是哪条规则、哪段时长、哪张券出了问题。

**真实约束**：计费输入包括轨迹、锁状态、时长、价格版本、优惠券、活动规则；轨迹可能缺失，锁可能延迟上报；支付通道可能超时；退款不能重复。

**方案**：

1. 计费事件化：行程开始/结束、轨迹点、锁开关、价格版本、券核销都作为事件；计费引擎按版本化规则计算，生成不可变账单快照。
2. 账单记录“规则版本、计费段、每段时长/里程、优惠明细、应付/实付”，客服能逐步展开；不是只存一个总金额。
3. 异常检测：对比“预估价、实收价、同行程历史均价、规则应得价”，命中差异生成工单；例如 1 公里内收 10 元、时长 0 分钟、券未抵扣。
4. 修正走“调整单/退款单”，不改原账单；退款单号唯一，先记账再退通道，失败重试+对账。

**关键取舍**：为什么不直接改账单金额？账单是审计凭证，改金额无法追溯；调整单保留原账单和原因。为什么不在计费时强依赖轨迹？轨迹会丢，计费要能用“锁状态+时长”兜底并标记。

**可讲的亮点**：把计费做成“可回放”：给定行程 ID 和价格版本，能重算出同一账单；客服从“猜为什么扣费”变成“看每一步”。示例：上线后计费类工单占比从 18% 降到 6%，退款处理时长从 2 天降到 4 小时。

**追问**：轨迹丢失怎么算？按最短/最长合理路径给区间并标记，人工可复核。重复计费？账单号/行程号唯一，支付回调幂等。优惠叠加顺序错？规则版本里固定“先折扣后券”，可回放验证。

## 四、司机接单距离优化

**面试官在考什么**：多目标调度：用户要快、司机要赚、平台要成交，不能只按最近排序。

**真实约束**：附近司机少、远郊司机不愿接、司机可能挑单/取消；高峰供需失衡；补贴有预算。

**方案**：

1. 召回：GeoHash/ES 取附近司机，过滤限行、车型、服务分、疲劳驾驶、已接单。
2. 评分：`接驾时间、司机预估收益、历史接单率、区域供需、乘客等待时长` 加权；远郊用“回程单优先/动态补贴”提升意愿，而不是无限加价。
3. 派单轮次：先给高评分司机，超时逐轮扩大半径/加补贴；同一司机短时间不重复打扰。
4. 灰度与指标：接单率、取消率、乘客等待、司机时薪、补贴 ROI；策略按城市灰度。

**关键取舍**：只按距离最近会让远郊永远没单；只按收益会让用户等太久。补贴是调节供给，不是长期价格战，要设预算和 ROI 上限。

**可讲的亮点**：把“远郊难打车”拆成“司机不愿空驶回程”，用回程单/顺路单解决，补贴成本比直接加价低；示例：远郊接单率从 45% 提到 68%，单均补贴下降 1.2 元。另一个亮点是取消率纳入司机评分，防止“先接再挑”。

**追问**：司机挑单怎么办？提高取消成本、派单冷却、服务分；但不能过度惩罚导致司机流失。乘客安全？夜间/偏远路线加行程分享/录音。供需预测错了？动态补贴 + 排队 + 预约。

## 五、顺风车行程拼单冲突

**面试官在考什么**：你能不能量化“顺路”，并处理车主、乘客、平台三方的时间/费用冲突。

**真实约束**：车主路线 A→B，乘客 A→C、D→B；拼单会绕行；车主有时间窗/座位/行李限制；路况会变。

**方案**：

1. 基础匹配：起终点距离、出发时间窗、座位/行李、是否接受宠物/绕行。
2. 枚举新乘客插入位置，计算新增里程、新增时间、费用分摊；设“最大绕行 20% 或 15 分钟”阈值，超阈值让乘客确认加价/改时间。
3. 拼单成功后重算每位乘客预计到达和费用，通知所有人；行程中路况导致超阈值，允许无责取消。
4. 车主违约/乘客爽约走信用分；费用争议按实际轨迹复核。

**关键取舍**：路线重叠度高不等于顺路，插入位置和绕行成本才是关键；不能只看起点距离。

**可讲的亮点**：把绕行成本量化成“分钟 + 米”，并在确认页明确展示“多花 12 分钟、多 3 公里”，把争议前置；示例：拼单投诉率下降 30%，因为用户事前知道绕行。

**追问**：动态路况怎么处理？行程中重算，超阈值触发确认。车主临时改路线？乘客可无责取消。费用怎么分？按实际乘坐段 + 人头/里程规则，账单明细可查。

## 六、跨城订单过路费分摊

**面试官在考什么**：费用透明与公平：谁坐哪段、谁承担哪段，不能总价平均分。

**真实约束**：高速门架、桥隧、改道、ETC 折扣、乘客上下车点；账单要能申诉。

**方案**：

1. 用门架/轨迹还原实际行驶路段，识别每段费用；地图路径做交叉校验。
2. 按“谁乘坐了哪一段”分摊：乘客只承担自己乘坐区间产生的费用，空驶段车主承担；多人共乘按规则分摊。
3. 账单展示路段、金额、分摊人数、乘客应付；支持 ETC 账单核对。
4. 争议走申诉，按轨迹/门架/支付流水复核；多收退款，少收补收要有依据。

**关键取舍**：总价平均分会让短途乘客为长途段买单，体验和合规都差；按段分摊更公平但实现复杂。

**可讲的亮点**：把过路费从“一笔糊涂账”做成“路段级明细”，客服能直接定位争议段；示例：过路费争议工单下降 40%，退款有据可查。

**追问**：门架数据缺失？按里程估算并标记“估算”，人工可复核。改道产生新费用？按实际轨迹重算，提前告知。ETC 折扣归谁？按平台规则，账单里写明。

## 七、换电柜电池状态同步

**面试官在考什么**：你能不能区分“物理在柜”“可租”“可预约”，而不是把数据库里的“在柜”直接当“可租”。

**真实约束**：电池会被换走、故障、离线、预约；设备上报可能乱序/延迟；用户到现场发现没电会投诉。

**方案**：

1. 设备/BMS 上报电池在位、SOC、健康、故障、柜门状态，事件带 `seq` 和时间戳；消费端按 `seq` 丢弃乱序旧事件。
2. DB 存物理状态（事实源），Redis 存“可租库存”视图；查询返回“可用数量 + 更新时间 + 预计可用”，不承诺精确到个。
3. 预约用 Lua 原子占用“柜门 + 电池位”，TTL 90 秒；到店核销或超时释放；预约键唯一防重复。
4. 心跳超时整柜降级为不可用；定时对账 DB 与 Redis，差异告警。

**关键取舍**：为什么不让用户看精确数量？库存瞬时变化，精确承诺放大投诉；分级展示更稳。为什么预约要锁柜门而不是只锁电池？换电要开门，柜门被占也会失败。

**可讲的亮点**：把“有满电”投诉拆成三类：数据延迟、电池故障、柜门占用；每类有不同提示和补偿，而不是统一说“系统问题”。示例：换电失败投诉下降 35%，预约核销率提升到 92%。

**追问**：Redis 挂了怎么办？读 DB 并降级展示，预约限流。电池到店发现故障？换柜/退预约并补偿。设备离线？整柜置灰，恢复后对账。超卖？DB 唯一约束 + 预约 TTL + 人工巡检。

## 八、换电订单超时计费

**面试官在考什么**：规则透明、阶梯计费、防恶意占用，同时避免天价账单。

**真实约束**：用户可能忘记归还、柜机离线、电池被占用；计费规则要下单前展示；押金/信用/买断要组合。

**方案**：

1. 订单状态机：`租出 → 使用中 → 已归还 / 超时 → 买断/赔付`；归还失败以“用户操作 + 设备事件”双证据。
2. 规则版本化：免费时长、小时费率、日封顶、押金抵扣；下单前展示，变更不追溯。
3. 延迟消息在到期前 15 分钟提醒，到期后按规则计费；重复触发按订单状态幂等。
4. 恶意占用用信用分、押金、黑名单、买断价约束；争议可申诉。

**关键取舍**：为什么不用定时扫全表？订单到期时间分散，延迟消息更高效；扫描只做兜底。为什么要封顶？天价账单会引发投诉和监管风险，封顶+买断更稳。

**可讲的亮点**：把“超时计费”做成“先提醒、后计费、可封顶、可买断”四段，投诉率明显下降；示例：超时争议从每月 200 单降到 60 单。另一个亮点是归还失败不直接判超时，先查柜机状态，避免设备问题让用户背锅。

**追问**：用户说已归还但柜机没记录？查柜门/电池 seq/视频，人工复核。押金不够？走信用/催收/黑名单。计费规则改了，老订单按哪版？按下单时版本，不追溯。

## 九、节假日骑行峰值应对

**面试官在考什么**：你知不知道扩容不是万能，瓶颈会转移；核心是保开锁、少排队、可回滚。

**真实约束**：国庆景区周边峰值可能是日常 5–10 倍；DB/Redis/第三方都可能成为瓶颈；扩容需要预热。

**方案**：

1. 节前预测热点区域，提前投放车辆、扩容服务、预热缓存；和下游确认配额。
2. 网关按 IP/用户/区域限流，排队/验证码削峰；开锁/关锁与推荐/轨迹分池隔离。
3. 扩容顺序：先扩 DB 连接/Redis/下游配额，再扩无状态服务；新节点预热后接流量。
4. 过载降级：保开锁/关锁，弱化推荐、轨迹、积分；事后补偿；开关可回滚。

**关键取舍**：只加机器会把压力传给 DB/Redis，反而打爆下游；扩容前先做全链路容量评估。

**可讲的亮点**：把“峰值预案”做成“分层降级清单”，每层有触发阈值和回滚人；示例：国庆峰值开锁成功率保持 99.5%，推荐降级 30% 流量，未出现 P0。另一个亮点是压测时故意打满 DB 连接，提前暴露连接池瓶颈。

**追问**：DB 顶不住怎么办？读写分离/热点缓存/排队；不能全量降级。缓存雪崩？随机 TTL + 互斥重建。扩容后仍超时？看下游和 GC，不要继续加机器。

## 十、优惠券领取并发控制

**面试官在考什么**：券库存和用户限领两个约束的原子性，以及 Redis/DB 不一致时的兜底。

**真实约束**：大量用户同时抢券；券可能超发；同一用户重复领；MQ 可能重复消费。

**方案**：

1. Redis Lua 原子执行“查库存 + 查用户已领 + 扣库存 + 标记用户”，一次 RTT 完成，避免先查再扣的竞态。
2. 领取成功发 MQ 异步落库/发券；DB 唯一索引 `(user_id, coupon_id)` 兜底。
3. 失败回补 Redis 库存；已领用户重复请求返回原结果。
4. 对账：Redis 扣减、券记录、发放流水核对。

**关键取舍**：为什么不用分布式锁？锁等待/超时/续期拉高尾延迟；短临界区用 Lua 更合适。为什么还要 DB 唯一索引？Redis 可能丢数据/主从切换，DB 是最后防线。

**可讲的亮点**：把“库存”和“限领”放在同一个 Lua，避免两次 RTT 中间被并发穿插；示例：10 万 QPS 下零超发，Redis 故障时自动停领而不是打穿 DB。另一个亮点是领券结果页做“处理中”状态，避免用户重复点。

**追问**：Redis 挂了怎么办？停领/限流，不透传 DB；MQ 重复消费？业务键幂等；超发怎么回收？唯一约束 + 对账 + 人工回收。

## 十一、跨平台账户数据同步

**面试官在考什么**：多端（App/支付宝/微信）账户统一，余额/券/记录不能各存一份。

**真实约束**：openId 只是绑定关系；余额变动涉及资金；同步有延迟；解绑/换绑要安全。

**方案**：

1. 统一 `userId`，三方 openId 只做绑定；余额/券/记录以账户中心为事实源。
2. 跨端登录用统一 Token；绑定/解绑走短信/人脸校验；变更发事件总线。
3. 各端本地缓存带版本号/时间戳，收到事件失效；冲突按“服务端最新 + 业务规则”合并。
4. 最终一致 + 对账；余额变动用流水，关键操作回源。

**关键取舍**：跨端强一致成本高；余额用“账户中心 + 流水”保证最终一致，展示可短暂旧值，支付时校验。

**可讲的亮点**：把 openId 降级为“登录别名”，避免多套账户各自记余额；示例：跨端余额投诉从每月 50 单降到 5 单，靠的是“支付前回源 + 事件失效”。另一个亮点是解绑时先冻结余额/券，防止用户钻空子。

**追问**：同步延迟用户看到旧余额？展示“处理中”，支付回源。重复绑定？唯一约束 + 幂等。异地登录？设备指纹/风控/二次验证。

## 十二、订单分账数据准确

**面试官在考什么**：分账不是算比例，而是规则版本、明细、结算、对账四件事。

**真实约束**：合作方多、比例/固定/阶梯规则、退款、结算周期、支付通道回执。

**方案**：

1. 分账规则版本化，绑定合同与生效时间；规则变更不追溯已结算订单。
2. 每笔订单生成分账明细：参与方、金额、规则版本、计算过程；唯一键 `(order_id, partner_id)`。
3. 先记账后结算；结算走支付通道并回执；失败重试/对账。
4. 与订单、支付流水、合作方账单对账；差异挂账人工处理。

**关键取舍**：只存分账总额无法解释每个参与方拿多少，也无法对账；必须明细化。

**可讲的亮点**：把分账做成“订单级明细 + 规则快照”，财务能逐笔追到规则；示例：月度分账差异从 0.3% 降到 0.02%。另一个亮点是退款时按原分账明细反向冲正，不重新算比例。

**追问**：规则变更影响老订单吗？不追溯，按订单发生时版本。支付失败？重试 + 挂账。合作方对账不一致？拉明细逐笔核，差异工单。

## 十三、第三方定位服务降级

**面试官在考什么**：定位是增强能力，不能成为核心骑行/接单的硬依赖；降级要明确、可解释。

**真实约束**：GPS/基站/WiFi 多源；第三方超时；定位精度/新鲜度不同；跨区调度涉及安全。

**方案**：

1. 多源定位按精度/新鲜度加权；第三方超时用缓存/最后位置兜底，返回 `accuracy`、`timestamp` 和“可能不准”标记。
2. 开锁/关锁用车辆蓝牙/二维码/柜机状态，不依赖精确定位；接单用区域中心点兜底。
3. 高风险操作（跨区调度、夜间偏远）要求更高精度，不满足则限制。
4. 恢复后纠偏，异常订单人工复核。

**关键取舍**：缓存位置不能假装准确；要标注，让前端提示用户。定位完全不可用时，保开锁但限制高风险。

**可讲的亮点**：降级不静默：返回精度和时间戳，客服能看到“当时定位是 500 米/3 分钟前”；示例：定位故障期间开锁成功率不受影响，相关投诉可解释。另一个亮点是把定位降级和风控联动，夜间偏远订单要求二次确认。

**追问**：缓存多久？按业务定 TTL，越久越不准。跨区判断？用区域中心点 + 用户确认。定位漂移？多源校验 + 轨迹平滑。

## 十四、支付服务故障兜底

**面试官在考什么**：支付未知状态的处理：不能重复扣款，也不能让用户无限挂账。

**真实约束**：支付通道超时/掉单；用户拒付/恶意欠费；下次骑行前要拦截；退款要幂等。

**方案**：

1. 支付状态机：`待支付 → 支付中 → 成功/失败/未知`；未知状态主动查询，不直接判失败。
2. 故障时允许“信用骑行/后续补付”，按信用分/历史行为决定；高风险用户仍拦截。
3. 掉单用定时对账/支付查询补偿；欠费在下次骑行前提示/拦截。
4. 恢复后自动扣款或推送补付；坏账走催收/核销。

**关键取舍**：全部放行会放大坏账；全部拦截会误伤好用户。信用分级是折中。

**可讲的亮点**：未知状态不判失败，先查后补，避免“用户已付又重复扣”；示例：支付故障期间坏账率控制在 0.5% 以内。另一个亮点是补付链路给“下次骑行前”缓冲，不当场卡死用户。

**追问**：重复支付怎么退？支付流水去重 + 退款单。用户不补付？信用分/限制/催收。支付成功但订单未更新？回调 + 对账修复。

## 十五、FullGC 频繁

**面试官在考什么**：你能不能区分“泄漏”和“峰值/大对象”，而不是一上来调参数。

**真实约束**：8G/16G 堆、G1、容器化；dump 会影响服务；重启只能止血。

**方案**：

1. `jstat -gcutil` 看 GC 频率、老年代回收后是否回落；G1 日志看 Humongous、Mixed GC。
2. `jcmd GC.heap_dump`/`jmap` 拿 dump，MAT 看支配树、GC Roots、大对象、线程栈。
3. 常见根因：本地缓存无上限、批量查询一次加载、ThreadLocal 累积、大 JSON、元空间/CodeCache 满。
4. 先止血（限流/扩容/重启），再改代码/缓存/查询；参数调整最后做并压测。

**关键取舍**：如果回收后老年代回落，多半是峰值/大对象；不回落才像泄漏。重启前摘流，保留 dump。

**可讲的亮点**：先看“回收后是否回落”再决定查泄漏还是扩容，避免盲目加堆；示例：定位到本地缓存无上限，修复后 FullGC 从每天 12 次降到 1 次。另一个亮点是把 dump 分析做成 checklist，团队都能按步骤查。

**追问**：G1 Humongous 怎么产生？大对象超过 Region 一半；减少大数组/大字符串。dump 影响性能？摘流/低峰/`jcmd`。参数怎么调？先压测，别拍脑袋。

## 十六、CPU 使用率过高

**面试官在考什么**：线程级定位：GC、锁竞争、计算密集、死循环、线程过多。

**真实约束**：容器 CPU 限额、GC 线程、业务线程池、下游超时重试。

**方案**：

1. `top -Hp <pid>` 找高 CPU 线程，`printf "%x"` 转十六进制，`jstack` 找栈。
2. 看 GC 线程占比（GC 问题）、RUNNABLE 业务线程（计算/循环）、BLOCKED（锁）。
3. `async-profiler`/火焰图定位热点方法；结合日志看某类请求突增。
4. 优化算法/缓存/批量/并发；线程池隔离；必要时限流。

**关键取舍**：CPU 高不一定是代码计算，可能是 GC 或锁自旋；先定位再扩容。

**可讲的亮点**：先看 GC 线程占比，再谈业务代码；示例：CPU 100% 最终定位到正则回溯，改预编译/限制长度后恢复。另一个亮点是保留现场（线程栈/火焰图），事后能复盘而不是重启了事。

**追问**：容器里 top 看不到宿主线程？用 `jstack` + `pid` 映射/cgroup。死循环？看 RUNNABLE 栈。锁竞争？看 BLOCKED 和锁持有时间。

## 十七、热点换电柜缓存设计

**面试官在考什么**：读多写少、热点集中、状态变化快；缓存要挡流量，但不能展示过期库存。

**真实约束**：热门商圈柜查询 QPS 高；电池状态秒级变化；缓存击穿/大 key；多实例本地缓存一致性。

**方案**：

1. Caffeine 本地 + Redis 两级；key 按柜/区域分片，避免大 key；本地 TTL 200ms–1s，Redis 1–5s。
2. 缓存值带版本号/更新时间；状态变更发事件失效；查询返回“可用数量/预计可用”。
3. 预约用 Lua 占位；DB 为事实源，定时对账修正缓存。
4. 热点 key 本地挡主流；缓存击穿用互斥重建/逻辑过期。

**关键取舍**：TTL 太长会放大“有满电到现场没有”；太短会打穿 DB。按业务接受度定，展示数量而不是精确承诺。

**可讲的亮点**：把缓存 TTL 和“可租承诺”分开：展示用短 TTL，预约用 Lua 实时占位；示例：热点柜 DB QPS 降 80%，换电失败投诉降 35%。另一个亮点是本地缓存带版本，事件丢失也能短时间收敛。

**追问**：Redis 挂了？降级读 DB + 限流；本地与 Redis 不一致？版本/短 TTL；大 key？按柜拆分，UNLINK 删除。

## 十八、骑行历史数据归档

**面试官在考什么**：冷热分离、查询路由、可追溯；归档不是删除。

**真实约束**：亿级订单、历史查询低频但必须能查；监管/争议要能找回；归档不能影响线上。

**方案**：

1. 近期表保留 3–12 个月热数据，历史表/对象存储存冷数据；按时间分区。
2. 归档任务分批、可重入、可回溯；归档前校验，归档后标记；保留 ID 映射。
3. 查询按时间路由：近期查热库，历史查冷库/ES；索引只保留必要列。
4. 对账：归档条数、金额、用户记录一致。

**关键取舍**：归档后不能随意删源数据；要保留可追溯窗口。深分页查询成本高，要限制范围。

**可讲的亮点**：归档不是“删旧数据”，而是“热库瘦身 + 冷库可查 + ID 映射可追”；示例：热表从 8 亿降到 1.2 亿，查询 P99 从 800ms 降到 120ms。另一个亮点是归档任务可重入，失败重跑不重复。

**追问**：用户要查 3 年前订单？按 ID 路由冷库/ES。归档失败？重试 + 对账。合规删除？保留删除标记，按法规处理。

## 十九、用户身份校验防刷

**面试官在考什么**：脚本伪造骑行订单骗补贴，单靠 IP/验证码不够；要设备、行为、关系、资金四层。

**真实约束**：黑产会换设备/代理；误杀正常用户有成本；补贴预算有限；案件要可追溯。

**方案**：

1. 设备指纹、SIM/网络、安装列表、传感器异常；接口签名/防重放。
2. 行为序列：下单频率、路线合理性、停留时长、退款/投诉模式；例如短时间跨区、原地长时长、反复取消。
3. 规则引擎 + 模型评分；高风险挑战验证码/人脸/人工；黑名单/灰名单。
4. 案件沉淀，策略灰度，误杀申诉。

**关键取舍**：全部强验证会伤体验；分层验证才是平衡。规则要可解释，模型要可回滚。

**可讲的亮点**：把“路线合理性”做成特征：正常骑行速度/路径/停留，异常订单一眼能看出；示例：某活动骗补减少 70%，误杀率控制在 2% 以内。另一个亮点是案件库，黑产换号也能关联设备/收款账户。

**追问**：误杀怎么办？申诉 + 人工复核 + 白名单。团伙怎么识别？设备/支付账户/位置关联图。模型效果下降？规则兜底 + 灰度。

## 二十、骑行路线智能推荐

**面试官在考什么**：多目标路径规划：时间、安全、舒适、距离，不是单纯最短路。

**真实约束**：路网、实时路况、自行车道、坡度、施工/事故；新区域数据稀疏；推荐要可解释。

**方案**：

1. 构建路网图，边权重含距离、坡度、自行车道、拥堵、事故/施工。
2. A*/双向搜索召回候选，再按“时间、安全、舒适、距离”多目标排序；给推荐理由（更快/更安全）。
3. 实时路况定时更新；数据稀疏回退默认路线；收集用户选择/反馈迭代权重。
4. 推荐错误可切换；安全权重可配置。

**关键取舍**：多目标不能简单加权成单一分数，容易牺牲安全；用帕累托候选/可解释权重。

**可讲的亮点**：把“安全”做成可解释权重，推荐页告诉用户“这条路多 3 分钟但少 2 个机动车路口”；示例：推荐采纳率提升 15%，事故相关投诉下降。另一个亮点是新区域回退到通用路网，不让用户无路可走。

**追问**：实时路况不可用？用历史权重。新区域没数据？回退步行/骑行通用路网。推荐绕路？给理由 + 可切换。

## 小结

- 哈啰 20 题的核心是“调度、库存、计费、资金、稳定性”五类，每题都要落到状态机、数据模型、失败兜底和对账。
- 面试时先讲业务约束和取舍，再讲方案；亮点要带数字和“为什么”，不要只报框架名。
- 数字是示例，换成你的真实项目；没做过就讲推演，别编经历。
