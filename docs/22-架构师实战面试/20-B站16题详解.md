# B 站 16 题详解：内容、弹幕与高并发

> 定位：B 站后端 16 题逐题深答。每题按“面试官想听 → 具体方案 → 关键取舍 → 可讲的亮点 → 追问”写，重点讲内容链路、弹幕洪峰、最终一致与降级。数字是示例口径，面试时替换成你的真实值；没做过就讲推演，不编经历。

## 一、自我介绍 + 项目

**面试官想听**：你有没有做过“内容平台”的真实链路：上传、审核、推荐、弹幕、稿件状态；峰值怎么扛；出过什么事故。

**答法**：背景给日活、投稿量、弹幕峰值、存储规模；目标给上传成功率、审核时长、弹幕延迟、P99；动作讲 2–3 个关键设计，例如“临时文件 + 本地消息表”“弹幕分层限流”“分库分表 + 异构索引”；结果给数字；反思讲边界。

**关键取舍**：B 站面试官对内容链路很熟，别泛泛说高并发；选一个你真做过的链路，讲清“正常路径 + 异常路径”。

**亮点**：讲一个“投稿失败但文件已上传”的坑，以及你怎么用临时空间 + 对账解决，比背框架更有说服力；示例：孤儿文件从每天 500 个降到 0。

**追问**：你负责投稿还是弹幕？最大峰值多少？如果重做会改什么？

## 二、分布式事务：投稿“文件 + 凭证 + 记录”

**面试官想听**：对象存储与 DB 跨系统，文件成功/记录失败、记录成功/文件失败怎么处理。

**方案**：

1. 先传临时空间，拿 `uploadId`/对象 key；稿件记录只引用 key，不搬文件。
2. 本地事务写“稿件记录 + 本地消息表”；消息投递合并/转正/审核。
3. 消费幂等 `(userId, uploadId)`；失败重试、死信、补偿。
4. 定期清理无引用临时文件；对账“记录↔对象”。

**关键取舍**：为什么不用 2PC？对象存储不支持，长事务会阻塞；临时文件 + 本地消息表更适合跨系统。记录失败时文件不立即删，留给生命周期清理。

**亮点**：投稿不是“传完就写库”，而是“临时文件 + 最终引用”；示例：合并失败可重试，用户不用重传 20GB。另一个亮点是每日对账“对象存储有文件、DB 无记录”，自动清理/补偿。

**追问**：记录成功文件失败？稿件标记“处理中”，重试/回滚。审核消息丢？本地消息表重投。重复投稿？`uploadId` 幂等。

## 三、弹幕 100 倍峰值：跨年/晚会

**面试官想听**：写多读多、允许延迟/采样；保直播不崩，不是每条都永久不丢。

**方案**：

1. 网关按房间/用户/全局多级限流；同用户频控，黑名单/关键词前置。
2. 接入层本地缓冲/批量写，削峰；按房间分区，防热房间打爆。
3. 异步 MQ → DB/冷存；在线只推最近窗口。
4. 过载降级：采样、延迟展示、只保高价值、关闭历史回放；恢复后补。

**关键取舍**：弹幕要“分层可丢”：付费/高价值尽量不丢，普通可采样；全量持久化成本高，直播结束再落库更稳。

**亮点**：峰值 100 倍时直播不卡，弹幕延迟 <3 秒；示例：热门房间单独扩容，普通房间不浪费资源。另一个亮点是降级有开关/阈值，恢复后自动回补。

**追问**：弹幕能丢吗？产品先定义。队列满？丢弃非核心并标记。消费失败？重试 + 对账。

## 四、缓存一致性：昵称同步用户中心/弹幕/空间

**面试官想听**：读极多写极少、多系统缓存；事件广播、版本、短 TTL。

**方案**：

1. 用户中心为事实源；改昵称更新 DB，发事件（含版本号）。
2. 各系统订阅：删本地/Redis 缓存，或更新新值；本地短 TTL 兜底。
3. 展示允许短暂旧值；身份/合规场景回源。
4. 监控不一致时长；对账。

**关键取舍**：昵称不是“每个系统各自查”，而是“一次变更，事件广播”；事件可能丢，短 TTL 是最后收敛手段。

**亮点**：昵称不一致投诉从每月 30 单降到 3 单；示例：旧版本事件丢弃，防覆盖新值。另一个亮点是展示层带“资料更新中”，用户可理解。

**追问**：为什么不双写？非原子/冲突。事件丢失？TTL/定时拉取。旧值覆盖？版本号。

## 五、分库分表：用户 ID + 时间 + 分区

**面试官想听**：分片键、查询维度、跨分片聚合、扩容。

**方案**：

1. 主表按 `userId` 哈希分库，按时间分表/分区；稿件 ID 全局唯一。
2. 稿件维度建异构表/ES；时间范围走分区裁剪。
3. 跨分片聚合走离线/汇总表；避免大范围扫描。
4. 路由表/基因法关联用户与稿件。

**关键取舍**：按用户分片保写入，按稿件查询靠异构索引；不要指望一个分片键支持所有查询。

**亮点**：投稿写入 P99 从 300ms 降到 80ms；示例：稿件查询走 ES，主库不被聚合拖垮。另一个亮点是扩容用双倍/一致性哈希，迁移可回滚。

**追问**：为什么按用户不按稿件？投稿是用户维度写。跨分片查？异构/ES。扩容？双倍迁移。

## 六、分布式锁：一键三连防重复

**面试官想听**：组合操作防重复，但锁不是原子性；每个子动作要幂等。

**方案**：

1. Redis 锁 `(userId, upId, type)`，`SET NX EX`；拿不到返回处理中。
2. 子动作独立幂等：`(userId, videoId, type)` 唯一；点赞/投币/收藏分别记账。
3. 组合用状态机/本地消息表，部分失败可重试。
4. 锁粒度到用户-稿件，不做全局锁。

**关键取舍**：一键三连不是“一个事务”，而是“三个幂等动作 + 组合状态”；锁超时也不能保证唯一，DB 唯一键兜底。

**亮点**：连点 10 次只生效 1 次；示例：投币走账务流水，锁超时也不会重复扣。另一个亮点是部分失败可重试，不强行全部回滚。

**追问**：为什么不用大锁？串行化所有用户。锁超时？DB 唯一约束。部分失败？重试/补偿。

## 七、消息可靠：审核通过通知推荐/粉丝/统计

**面试官想听**：审核结果多下游通知，不能丢、不能重复；不同下游重要性不同。

**方案**：

1. 审核结果落库 + 本地消息表；投递 MQ。
2. 消费者幂等：推荐按稿件版本、粉丝按 `(upId, videoId, fanId)`、统计按稿件 ID。
3. 失败重试 + 死信 + 补偿；关键通知单独 topic。
4. 对账：审核通过列表 ↔ 各下游处理记录。

**关键取舍**：通知是“至少一次”，端到端靠业务幂等；不同下游可分级，不要求所有下游同时成功。

**亮点**：审核通过到推荐生效 <30 秒；示例：粉丝通知失败不阻塞推荐，死信补偿。另一个亮点是本地消息表扫描重投，不依赖 MQ 不丢。

**追问**：Kafka 怎么不丢？acks=all、幂等 producer、手动提交、副本。重复消费？业务幂等。下游不可用？降级/延迟。

## 八、一键三连：点赞、投币、收藏的并发与一致

**面试官想听**：三个动作语义不同：点赞可取消、投币扣钱、收藏是列表；不能一个计数器糊弄。

**方案**：

1. 点赞：Redis 计数 + DB 明细；取消幂等；防刷。
2. 投币：扣硬币走账务流水，唯一键防重复；失败回滚。
3. 收藏：关系表唯一键；列表分页。
4. 组合返回各部分结果；部分失败可重试。

**关键取舍**：投币和点赞分开可靠性：投币必须账务正确，点赞可弱一致；不要为了“三连原子”把资金和计数绑死。

**亮点**：投币重复 0，点赞计数最终一致；示例：点赞明细可对账，防计数漂移。另一个亮点是投币失败回滚硬币，不让用户白扣。

**追问**：三连必须原子吗？产品不必须；资金要独立可靠。点赞取消？幂等。计数与明细不一致？对账修复。

## 九、库存：秒杀/限定周边

**面试官想听**：少库存高并发、防超卖、限购、未支付释放。

**方案**：

1. Redis 预热库存，Lua 原子扣减 + 用户限购。
2. DB `stock >= n` 条件更新兜底；订单唯一键。
3. 未支付延迟释放；失败回补。
4. 对账：Redis、DB、订单。

**关键取舍**：Redis 预扣 + DB 兜底，不是“只信 Redis”；Redis 故障要停售/限流，不能打穿 DB。

**亮点**：峰值 5 万 QPS，超卖 0；示例：未支付释放让库存利用率提升 20%。另一个亮点是库存流水可对账，超卖能定位。

**追问**：为什么不直接 DB 扣？热点行竞争。Redis 丢数据？DB 兜底。重复扣？幂等。

## 十、接口 600ms 降到 100ms

**面试官想听**：先分解再优化；串行 RPC、重复查询、大对象、GC。

**方案**：

1. 埋点看 DB/RPC/缓存/序列化占比。
2. 批量/合并查询；串行改并行，隔离线程池 + 超时。
3. 加缓存、优化索引、限制字段；异步非核心。
4. 压测回归。

**关键取舍**：最大收益常是“少调用一次”，不是“换框架”；并行要有超时预算，否则尾延迟更差。

**亮点**：6 次 RPC 合并 2 次，600ms→100ms；示例：P99 从 900ms 降到 150ms。另一个亮点是并行线程池按下游隔离，慢下游不拖累全链路。

**追问**：P99 还高？排队/GC/热点。并行线程池？隔离。缓存一致性？回源。

## 十一、会话：多端登录与踢下线

**面试官想听**：共享、过期、注销、踢下线、防劫持。

**方案**：

1. Session/Token 存 Redis，带 userId、设备、过期；Cookie 只存 ID。
2. 登录生成新会话，旧设备可踢；异地风控。
3. 注销删除；敏感操作二次校验。
4. Redis 故障降级重登/本地短缓存。

**关键取舍**：JWT 无状态但难踢下线；服务端 Session 可控性更强。短期 Token + 黑名单是折中。

**亮点**：盗号后 1 分钟全端失效；示例：设备绑定 + 风险评分防劫持。另一个亮点是会话 ID 轮换，防固定攻击。

**追问**：JWT 适合吗？短期可以，踢下线难。Redis 挂了？重登。多端？设备维度。

## 十二、安全防护：越权、注入、CSRF、风控

**面试官想听**：认证、授权、输入、输出、风控分层；WAF 不是全部。

**方案**：

1. 认证 OAuth/Token，防重放；授权按用户/资源校验，不信任前端。
2. 输入校验、预编译 SQL、白名单；上传校验类型/大小/内容。
3. 输出 XSS 转义、CSP；敏感信息脱敏。
4. 风控频率/设备/行为/黑名单；审计日志。

**关键取舍**：越权要靠业务鉴权，不是 WAF；上传安全不只看后缀，要看内容/大小/解码。

**亮点**：水平越权测试覆盖所有资源接口；示例：上传恶意文件被内容检测拦截。另一个亮点是审计日志可追溯，安全事件能复盘。

**追问**：WAF 能替代代码安全吗？不能。越权怎么测？自动化遍历。CSRF？Token/SameSite。

## 十三、50 万 QPS 限流

**面试官想听**：网关集群 + 本地兜底 + 分级配额 + 防重试。

**方案**：

1. 网关按接口/用户/租户限流；Redis/Lua 分片计数。
2. 服务本地令牌桶兜底；集群限流故障保命。
3. 核心保配额，非核心降级；排队/429。
4. 压测、动态阈值、监控拒绝率。

**关键取舍**：50 万 QPS 不能单机精确限流，必须分层；本地限流只兜底，不能替代全局配额。

**亮点**：峰值 60 万，核心通过率 99%，非核心降级 40%；示例：租户配额防单租户打满。另一个亮点是 429 带重试时间，减少盲目重试。

**追问**：为什么不用单机令牌桶？不精确。Redis 热 key？分片。重试风暴？退避。

## 十四、补偿与 Canal

**面试官想听**：补偿处理失败后的最终一致；Canal 处理 DB 变更同步；两者都要幂等/对账。

**方案**：

1. 补偿：事务状态/步骤落库，失败重试队列，指数退避、死信、人工；资金冲正记账。
2. Canal：binlog → MQ → ES/缓存；按主键保序，消费幂等。
3. 全量 + 增量切换；位点/延迟监控；对账。
4. 补偿与同步都防重复/乱序。

**关键取舍**：Canal 不能替代业务消息，它是数据同步；补偿不能保证成功，只能最终一致 + 人工。

**亮点**：ES 与 DB 差异 <0.01%；示例：全量重建可切换，不怕 mapping 变更。另一个亮点是补偿分级，自动/人工分明。

**追问**：Canal 能 exactly-once 吗？端到端靠幂等。补偿失败？死信/人工。顺序？主键分区/版本。

## 十五、高可用：直播/投稿链路

**面试官想听**：核心/非核心分级、隔离、降级、容量、演练。

**方案**：

1. 核心链路（上传、播放、弹幕接入）多副本、跨可用区；非核心可降级。
2. 限流/熔断/隔离/超时/重试；防雪崩。
3. 缓存/队列削峰；DB 主从/分片；对象存储多区。
4. 预案、演练、告警、值班；RTO/RPO。

**关键取舍**：高可用不是“全链路多活”，是“核心保命 + 非核心可降级”；多活成本/一致性复杂，按业务定。

**亮点**：机房故障 5 分钟切流，播放不中断；示例：演练按故障剧本，不只看监控。另一个亮点是降级开关可回滚，避免“降级后忘了恢复”。

**追问**：多活一定好吗？成本/一致性。机房故障？切流。依赖故障？降级。

## 十六、20GB 视频上传

**面试官想听**：分片、断点续传、秒传、直传、合并校验、清理。

**方案**：

1. 前端分片 5–10MB，算文件 hash；初始化上传会话。
2. 服务端返回预签名 URL，直传对象存储；记录已传分片。
3. 断点续传查已传分片；秒传按 hash 查重。
4. 合并、校验 MD5/大小、转码/审核异步；临时分片清理。

**关键取舍**：20GB 不能过应用服务器，必须直传对象存储；分片会话要超时清理，防存储泄漏。

**亮点**：上传成功率 99.5%，应用带宽成本降 80%；示例：断点续传让弱网用户不用重传。另一个亮点是秒传按 hash + 大小，防误判。

**追问**：为什么直传？减少应用带宽/内存。合并失败？重试。秒传误判？hash + 大小。并发上传？限流。

## 小结

- B 站 16 题的核心是“内容链路 + 弹幕洪峰 + 最终一致”。
- 投稿用临时文件 + 本地消息表 + 幂等；弹幕要限流、缓冲、采样、降级。
- 昵称同步靠事件 + 版本 + 短 TTL；分库分表按查询维度建异构索引。
- 一键三连拆开做幂等，资金动作独立可靠；20GB 上传靠分片/断点/秒传。
