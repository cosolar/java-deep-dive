# 国产数据库适配与迁移：达梦、OceanBase 与 GaussDB

> 定位：信创替代不是「换个驱动」，而是把一套跑了十年的 Oracle/MySQL 应用迁到国产库——SQL 方言、事务语义、执行计划、备份恢复全都要重新验证。这篇不吹任何产品，讲清三类国产库的架构差异、迁移的五个阶段、以及「双跑对账 + 可回滚」这套把风险压住的工程方法。

> **版本提示（2026-11）**：达梦 DM8、OceanBase 4.x、openGauss/GaussDB 5.x 为常见生产版本；各产品的兼容模式与函数支持随版本变化，落地前以对应版本文档为准。

## 一、为什么需要单独设计

国产化迁移真正贵的地方，不是买 license，而是这四类隐性成本：

1. **SQL 方言**：Oracle 的 `ROWNUM`、`NVL`、`DECODE`、`(+)` 外连接，MySQL 的 `LIMIT`、`GROUP_CONCAT`，换库后要么改写、要么靠兼容模式。
2. **事务与锁**：隔离级别默认值、锁粒度、`SELECT ... FOR UPDATE` 行为差异，会改变并发正确性。
3. **执行计划**：同一条 SQL 在 A 库走索引、在 B 库全表扫；优化器对统计信息、Hint 的敏感度不同。
4. **运维体系**：备份恢复、主备切换、监控指标、扩容方式，全部要重建 SOP。

> 一句话：**迁移是「应用 + SQL + 数据 + 运维」四件事一起迁**，只迁数据必翻车。

## 二、核心原理

### 2.1 三类产品的架构差异

| 产品 | 架构 | 兼容取向 | 迁移友好度 | 典型场景 |
|---|---|---|---|---|
| 达梦 DM | 集中式（主备/读写分离） | Oracle 兼容模式较强 | 从 Oracle 迁较友好 | 传统 OLTP、替换 Oracle |
| OceanBase | 原生分布式（Paxos 多副本） | MySQL 兼容模式 | 从 MySQL 迁较友好 | 高并发、大容量、金融核心 |
| openGauss / GaussDB | 集中式 + 分布式两个形态 | PostgreSQL 内核 + Oracle 兼容 | 从 PG/Oracle 迁均可 | 政企、混合负载 |

**关键认知**：分布式库（OceanBase）的「分区键」会变成新的设计约束——原来单机随便写的 SQL，跨分区后可能变成跨节点查询，性能断崖。集中式库（达梦）迁移简单，但扩展性靠主备/分库，容量上限要提前算。

### 2.2 兼容模式能解决多少

三类兼容能力的边界：

| 能力 | 兼容模式能做 | 仍需改造 |
|---|---|---|
| 语法 | 大部分 `NVL`/`DECODE`/`ROWNUM` 可映射 | 存储过程、包、触发器、自定义函数 |
| 类型 | `NUMBER`/`VARCHAR2` 自动映射 | 精度、长度、时区语义 |
| 行为 | 部分隔离级别可配 | 锁等待、死锁检测、序列缓存 |
| 优化 | 提供 Hint | 执行计划仍需逐条验证 |

> 结论：**兼容模式降低「能不能跑」的门槛，不解决「跑得好不好」**。真实工作量在 SQL 重写与计划调优。

### 2.3 迁移的五个阶段

```
1 盘点 → 2 评估 → 3 改造 → 4 双跑对账 → 5 灰度切换
```

```mermaid
flowchart LR
    A["1 盘点<br/>库/表/SQL/存储过程"] --> B["2 评估<br/>兼容扫描 + 工时估算"]
    B --> C["3 改造<br/>SQL 改写 + 兼容层"]
    C --> D["4 双跑对账<br/>行数/主键/金额"]
    D --> E["5 灰度切换<br/>先读后写 + 可回滚"]
    E --> F{"对账一致?"}
    F -->|否| C
    F -->|是| G["下线旧库 + 复盘"]
```

1. **盘点**：库、表、SQL、存储过程、外链、定时任务、报表，形成清单与优先级。
2. **评估**：用迁移评估工具扫 SQL 兼容性，标记「自动兼容 / 需改写 / 不支持」；估算改造工时。
3. **改造**：SQL 改写、类型映射、序列/自增替换、分页语法、驱动与连接池升级；建立兼容层（DAO 层适配而非散落改写）。
4. **双跑对账**：新旧库同时写（或旧库写、新库同步），按主键/金额/行数比对，跑够一个业务周期（含月末、批量）。
5. **灰度切换**：按租户/流量比例切读、再切写；保留回滚开关与回滚窗口。

## 三、关键机制与参数

### 3.1 数据同步与双写

| 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 应用双写 | 实时、可控 | 代码耦合、失败要补偿 | 核心链路、短周期 |
| CDC 同步（binlog/日志） | 对应用透明 | 延迟、DDL 同步复杂 | 读流量切换、长周期双跑 |
| 批量导出导入 | 简单 | 停机、增量难 | 初始化、小库 |

**双跑期的核心是「对账」**：按天比对行数、主键集合、金额汇总；差异要能定位到具体行，而不是只知道「不一致」。

### 3.2 SQL 改写的六个高频点

| 原写法 | 常见改法 |
|---|---|
| `ROWNUM` 分页 | 改 `LIMIT/OFFSET` 或窗口函数 `ROW_NUMBER()` |
| `NVL(a,b)` | 改 `COALESCE(a,b)` / `IFNULL` |
| `DECODE` | 改 `CASE WHEN` |
| `(+)` 外连接 | 改标准 `LEFT JOIN ... ON` |
| 自增列/序列 | 改 `IDENTITY` / `SEQUENCE` / `AUTO_INCREMENT` |
| 隐式类型转换 | 显式 `CAST`，避免索引失效 |

### 3.3 执行计划验证

迁移后**每条核心 SQL 都要重新看计划**：

- 统计信息是否收集（新库常常空统计）；
- 索引是否建全（尤其函数索引、复合索引顺序）；
- 是否有隐式转换导致索引失效；
- 分区裁剪是否生效（分布式库尤其关键）；
- 绑定变量与字面量对计划的影响（参数化查询的计划稳定性）。

## 四、生产坑点与排查

### 坑点 1：兼容模式「能跑」，但性能差 10 倍

**现象**：SQL 在国产库能执行，但慢查询暴增。

**原因**：优化器不同、统计信息缺失、索引未迁、隐式转换。

**解法**：迁完先跑统计信息收集；逐条对比执行计划；对慢 SQL 建索引/改写；用 Hint 兜底。

### 坑点 2：分页语法差异导致结果错

**现象**：Oracle 的 `ROWNUM` 迁过去后分页数据重复/缺失。

**原因**：`ROWNUM` 与 `LIMIT` 语义不同（`ROWNUM` 在排序前生效）。

**解法**：统一改窗口函数 `ROW_NUMBER() OVER (ORDER BY ...)` + 外层过滤；测试边界（第 1 页、最后一页、空结果）。

### 坑点 3：NULL 与空串语义不同

**现象**：Oracle 里 `''` 等于 `NULL`，迁到 MySQL 兼容库后变成两个值，唯一索引/查询结果变化。

**解法**：业务层禁止空串与 NULL 混用；迁移时统一清洗；唯一索引考虑 NULL 语义。

### 坑点 4：序列/自增缓存导致主键跳号与冲突

**现象**：双写期间两边各自生成 ID，冲突或乱序。

**解法**：双写期由「统一发号器」生成主键，两库都用同一 ID；或一主一从（只一边生成）。

### 坑点 5：分布式库跨分区查询拖垮性能

**现象**：迁到 OceanBase 后，某些 join 慢 20 倍。

**原因**：分区键设计不合理，join 变成跨节点广播。

**解法**：按「高频 join 的关联键」设计分区键；大表用复制表/广播表；跨分区查询加限制与改写。

### 坑点 6：备份恢复没演练，真出事恢复不了

**现象**：切到新库后第一次故障，发现备份策略没配、恢复脚本跑不通。

**解法**：迁移前做一次「全量 + 增量」恢复演练，记录 RTO/RPO；切换后第一周每天校验备份可恢复。

### 坑点 7：驱动与连接池不兼容

**现象**：换库后连接泄漏、事务不生效、批量插入变慢。

**解法**：用官方推荐驱动版本；校验连接池的校验语句（`validationQuery`）、事务隔离配置；压测连接建立与回收。

## 五、调优与最佳实践

### 5.1 迁移风险控制

- **先读后写**：读流量先切，观察一周再切写；
- **按租户/业务线灰度**：先小客户，再核心；
- **保留双跑与回滚**：回滚开关要能在 5 分钟内生效；
- **冻结期**：切换窗口内禁止 DDL 与大批量任务；
- **对账自动化**：差异日报到人，不允许「大概一致」。

### 5.2 兼容层设计

不要在业务代码里到处写 `if (dbType == DM)`。做法：

- DAO 层统一封装分页、`COALESCE`、序列、批量插入；
- SQL 用 MyBatis 的 `databaseId` 提供多套语句（同一语义不同方言）；
- 把「方言差异」收敛到少数几个 Provider，避免散落。

### 5.3 落地清单

- [ ] 完成库/表/SQL/存储过程/定时任务全量盘点
- [ ] 用评估工具产出「兼容/需改/不支持」三档清单与工时
- [ ] 核心 SQL 逐条对比执行计划，统计信息已收集
- [ ] 双跑至少一个完整业务周期（含月末批量）
- [ ] 对账覆盖行数、主键集合、金额汇总，差异可定位到行
- [ ] 备份恢复演练过，RTO/RPO 有记录
- [ ] 灰度与回滚开关经过演练，5 分钟内可回
- [ ] 驱动、连接池、监控、告警全部接好

## 六、迁移项目管理：WBS、工时估算与风险登记

迁移最容易失控的地方是「评估时觉得两周能搞定，实际做了两个月」。把工作拆到可估算的粒度，再用风险登记册管住不确定性。

### 7.1 工作分解与估算口径

| 阶段 | 交付物 | 主要角色 | 估算口径（参考） |
|---|---|---|---|
| 盘点 | 库表清单、SQL 清单、存储过程清单、外链清单 | DBA + 开发 | 每库 2–5 人日，按表数量线性外推 |
| 兼容扫描 | 兼容/需改/不支持三档清单 | DBA + 迁移工具 | 扫描本身 1–2 人日，人工复核按 SQL 条数 |
| SQL 改造 | 改写后的语句 + 单测 | 开发 | 简单改写 0.5–1h/条，复杂 2–8h/条 |
| 存储过程改造 | 拆分后的存储过程/应用逻辑 | 资深开发 | 4–16h/个，含包与触发器 |
| 数据迁移 | 全量脚本 + 增量方案 | DBA | 按数据量与带宽估，留 30% 缓冲 |
| 双跑对账 | 对账任务 + 差异定位工具 | 开发 + DBA | 3–10 人日，取决于比对维度 |
| 灰度与回滚 | 开关、预案、演练记录 | 全员 | 至少 5 人日，含两次演练 |

一个可用的估算公式：

```
改造工时 ≈ SQL 条数 × 平均改写系数 + 存储过程数 × 8h
         + 接口数 × 2h（驱动/事务/批量） + 对账开发 5 人日
         + 演练 5 人日 × 2 次
```

> 经验值：**评估阶段给出的工时，乘以 1.5 再排期**。国产库的坑大多在「兼容模式能跑、但计划和锁行为不同」，这类问题只有压测和双跑才暴露。

### 7.2 风险登记册（迁移版）

| 风险 | 触发信号 | 缓解动作 | 退出条件 |
|---|---|---|---|
| 核心 SQL 计划退化 | 双跑期慢查询 Top20 出现新面孔 | 逐条对比计划、补统计信息、必要时 Hint | P99 不高于旧库 10% |
| 事务语义差异 | 并发用例出现脏写/重复扣减 | 隔离级别对齐、关键路径加唯一约束兜底 | 并发用例全绿 |
| 数据不一致 | 对账差异 > 0 且无法定位 | 差异落行、修同步链路、重跑对账 | 连续 3 个周期零差异 |
| 回滚不可用 | 演练时回滚超时或数据写不回 | 保留双向同步、回滚脚本纳入发布包 | 5 分钟内可回且验证过 |
| 运维能力缺口 | 新库告警无人认领、备份未演练 | 建 SOP、值班表、每月恢复抽验 | RTO/RPO 达标并留记录 |
| 驱动/连接池问题 | 连接泄漏、事务不生效 | 官方驱动、压测连接建立与回收 | 压测 24h 无泄漏 |

风险登记册要**每周更新一次**，每条都写清「谁负责、什么时候复查」。没有责任人的风险等于没登记。

## 七、SQL 与存储过程改写范式

改造不要从「见到 `NVL` 就替换」开始，而是按语义分类处理。下面六组是最常见的改写，附前后对照。

### 8.1 分页：`ROWNUM` → 窗口函数

```sql
-- 旧（Oracle）：ROWNUM 在 ORDER BY 之前分配，直接套会错
SELECT * FROM (
  SELECT t.*, ROWNUM rn FROM (SELECT * FROM orders ORDER BY created_at DESC) t
  WHERE ROWNUM <= 20
) WHERE rn > 10;

-- 新：窗口函数先排序再编号，语义明确
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (ORDER BY created_at DESC) AS rn
  FROM orders o
) t WHERE rn > 10 AND rn <= 20;
```

### 8.2 空值与条件函数

| 旧写法 | 新写法 | 注意 |
|---|---|---|
| `NVL(a, b)` | `COALESCE(a, b)` | 多参数场景 `COALESCE` 更通用 |
| `DECODE(x, 1, 'a', 2, 'b', 'c')` | `CASE x WHEN 1 THEN 'a' WHEN 2 THEN 'b' ELSE 'c' END` | 注意 `NULL` 走 `ELSE` |
| `(+)` 外连接 | `LEFT JOIN ... ON` | 过滤条件放 `ON` 还是 `WHERE` 会改变语义 |
| `SYSDATE` | `CURRENT_TIMESTAMP` | 时区语义要确认 |

### 8.3 批量插入与自增

- Oracle 的 `INSERT ALL` 要拆成多条 `INSERT` 或批量 API；
- 序列 `seq.NEXTVAL` 迁到 `IDENTITY`/`AUTO_INCREMENT` 后，**双跑期不要两边各自生成**，统一发号器给 ID；
- 批量插入用驱动批处理（JDBC `addBatch`）而不是循环单条，否则迁移后 RT 翻倍。

### 8.4 存储过程与包

存储过程是改造量最大的一块。推荐三种处理顺序：

1. **能上移的移到应用层**：校验、拼装、简单循环，放回 Service 层更好测；
2. **必须保留的拆小**：把大过程拆成「取数 → 计算 → 写回」三段，便于逐段对账；
3. **包/触发器尽量去掉**：触发器隐式写数据最难排查，迁移是清理它的好时机。

### 8.5 SQL 审核清单（改造后逐条过）

- [ ] 没有隐式类型转换（`WHERE id = '123'` 这类）
- [ ] 函数没有包在索引列上（`WHERE DATE(create_time) = ...`）
- [ ] 分页语句测试过首页、末页、空结果、总数为 0
- [ ] `NULL` 与空串语义在唯一索引与查询里都验证过
- [ ] 批量语句的 `fetchSize` / 批次大小压测过
- [ ] 事务边界没有跨库、跨服务

## 八、切换后 30 天的稳定性观察清单

切换完成不等于迁移结束。前 30 天是新库问题集中暴露的窗口，观察项要固定下来、责任到人。

| 频率 | 观察项 | 阈值信号 | 动作 |
|---|---|---|---|
| 每日 | 慢查询 Top20 与新增面孔 | 新 SQL 进入 Top20 且 P99 翻倍 | 拉计划对比，补统计/索引 |
| 每日 | 锁等待与死锁次数 | 死锁 > 0 且集中在同一业务 | 查事务顺序，缩短持锁时间 |
| 每日 | 连接数与活跃连接 | 活跃连接接近池上限 | 查泄漏、调池大小与超时 |
| 每日 | 主备/多副本延迟 | 延迟持续 > 1s | 查同步链路与网络 |
| 每日 | 对账差异 | 差异 > 0 | 定位到行、修链路、重跑 |
| 每周 | 统计信息与执行计划漂移 | 计划由索引变全表 | 重新收集统计、评估绑定变量 |
| 每周 | 容量与磁盘增长 | 周增幅超预期 50% | 查日志/临时表/归档 |
| 每周 | 备份恢复抽验 | 恢复失败或超 RTO | 修脚本、重演练 |

**回滚判据要提前写死**，不要临场拍脑袋：

| 情况 | 判断 | 动作 |
|---|---|---|
| 核心接口错误率 > 基线 3 倍，持续 10 分钟 | 不可接受 | 立即回滚读流量 |
| 出现资金/库存类数据不一致 | 不可接受 | 停止写流量、回滚、对账 |
| P99 高于旧库 50% 且 30 分钟内无改善 | 高风险 | 回滚并复盘计划问题 |
| 单点慢查询但可降级 | 可接受 | 限流/降级，24h 内修复 |

> 一条底线：**回滚不是失败，带着不确定继续跑才是**。回滚后把差异数据补齐、把根因写进复盘，下一次切换才不会重复踩。

## 九、迁移快问快答（补充）

| 问题 | 简短结论 |
|---|---|
| 先迁库还是先迁应用？ | 先做兼容层与 SQL 改造，应用能连新库再谈数据迁移 |
| 兼容模式开到最大就行吗？ | 不行。兼容模式影响优化器行为，要按业务验证计划，不是越大越好 |
| 双跑要跑多久？ | 至少一个完整业务周期，含月末/季末批量；核心系统建议 4–8 周 |
| 对账对哪些维度？ | 行数、主键集合、金额汇总、状态分布；差异必须能定位到行 |
| 分布式库一定要分区键吗？ | 是。没有合适分区键的表会退化成广播或单副本热点 |
| 迁移期间能做 DDL 吗？ | 切换窗口冻结 DDL；双跑期 DDL 要走双库同步流程 |
| 国产库的备份怎么验？ | 迁移前做全量+增量恢复演练，记录 RTO/RPO，切换后首周每日抽验 |
| 性能不达标先调什么？ | 统计信息 → 索引 → 隐式转换 → 分区裁剪 → 绑定变量计划 |
| 回滚要准备什么？ | 双向同步、回滚脚本、开关、演练记录；5 分钟内可生效 |
| 怎么说服业务方接受停机窗口？ | 用「灰度 + 读先切」把停机压到分钟级，给出回滚承诺与演练证据 |

## 十、五个危险信号

1. **兼容扫描「全部兼容」**：通常是扫描规则太宽，真实 SQL 还没覆盖存储过程与动态 SQL。
2. **统计信息为空就上线**：新库常见，计划会离谱；迁完先收集统计。
3. **双跑只对行数**：行数一致但金额/状态不一致，必须对比汇总与主键集合。
4. **回滚没演练**：文档写了不等于能用，切换前至少演练一次。
5. **只压测读、不压测写**：写路径的锁与序列才是迁移后最容易退化的地方。

**验收「三不」原则**：不双跑不上线、不对账不切写、不演练不回滚。任何一条被跳过，都要在复盘里写明原因与补偿措施——这是迁移项目最容易失守的地方。

## 十一、面试高频问法

**Q1：Oracle 迁国产库，最大的风险是什么？**
一句话结论：不是语法，是执行计划与事务语义的隐性差异。
展开：兼容模式能让 SQL 跑起来，但统计信息、索引、隐式转换会让性能差十倍；隔离级别与锁行为变化会影响并发正确性。
加分点：能说出「迁移是应用+SQL+数据+运维四件事一起迁」。

**Q2：双跑期怎么保证数据一致？**
一句话结论：统一发号 + 双向同步/双写 + 按主键与金额对账 + 差异可定位。
展开：ID 由统一发号器生成避免冲突；对账按天跑，差异落到具体行；跑够一个业务周期。
加分点：提到「对账任务自身要幂等、可重跑」。

**Q3：分布式库的分区键怎么设计？**
一句话结论：按高频 join/查询的关联键设计，减少跨节点查询，必要时用广播表。
展开：分区键选错会导致跨分区 join 与广播；大表可做复制表；注意分区裁剪。
加分点：能说出「单机 SQL 迁到分布式库，性能可能断崖」。

**Q4：`ROWNUM` 和 `LIMIT` 有什么区别？迁移怎么改？**
一句话结论：`ROWNUM` 在排序前生效，`LIMIT` 在排序后截取，语义不同。
展开：统一改 `ROW_NUMBER() OVER (ORDER BY ...)` 再过滤；测试首页/末页/空结果。
加分点：能指出「直接替换会导致分页重复或缺失」。

**Q5：迁移后慢查询暴增，怎么排查？**
一句话结论：先看统计信息与索引，再看隐式转换与分区裁剪，最后看计划是否退化。
展开：新库常缺统计信息；函数索引/复合索引未迁；`WHERE` 里隐式转换让索引失效。
加分点：能说出「绑定变量与字面量会让计划不稳定」。

**Q6：怎么保证迁移可回滚？**
一句话结论：双跑 + 读灰度 + 回滚开关 + 冻结期，四件套。
展开：先切读再切写；回滚开关 5 分钟内生效；切换窗口禁 DDL。
加分点：提到「回滚也要演练，不能只写在文档里」。

**Q7：国产库的兼容模式能省多少改造？**
一句话结论：省语法层的大部分，省不了存储过程、执行计划、事务语义。
展开：`NVL`/`DECODE`/`ROWNUM` 多可映射；包、触发器、自定义函数要重写；计划要逐条验。
加分点：能区分「能跑」与「跑得好」。

**Q8：选达梦、OceanBase 还是 openGauss？**
一句话结论：看存量技术栈与容量模型：Oracle 存量偏达梦，MySQL 存量高并发偏 OceanBase，PG 存量偏 openGauss。
展开：集中式 vs 分布式决定扩展方式；兼容模式决定改造成本；生态与运维能力决定长期成本。
加分点：能说出「分布式库会引入分区键这个新约束」。

## 小结

- 迁移是应用、SQL、数据、运维四件事一起迁，不只是换驱动。
- 兼容模式降低「能跑」门槛，不解决执行计划与事务语义。
- 五阶段：盘点 → 评估 → 改造 → 双跑对账 → 灰度切换。
- 分布式库会引入分区键约束，单机 SQL 可能性能断崖。
- 双跑的核心是对账，差异必须定位到行。
- 回滚能力要演练，不能只写在文档里。
