# 算法思维与复杂度：架构师的性能直觉

> 定位：架构师不需要刷几千道题，但必须能在三分钟内判断「这个方案的时间复杂度能不能扛住量级」「该用哈希、堆还是 B+ 树」「这段代码为什么会 O(n²)」。这一篇不讲具体题型，只讲三件事：复杂度怎么算、结构怎么选、复杂度怎么落到容量上。后面的数组、链表、树、图、DP 各篇，都是这套判断力的具体应用。

## 一、为什么架构师还要学算法

三个真实场景：

1. **容量估算**：一个接口在循环里调用 `list.contains()`，10 万条数据就是约 10⁹ 次比较。加到 8 台机器也只能把 10 秒变成 1.2 秒，换 `HashSet` 直接降到 10 万次。
2. **结构选型**：排行榜用 `ORDER BY`、`TreeSet` 还是堆？延迟队列用 `DelayQueue`、时间轮还是 Redis ZSet？选错不是「慢一点」，而是复杂度差一个量级。
3. **面试**：大厂架构岗仍会考手写 LRU、TopK、BFS、DP。考的不是背诵，是边界、复杂度与取舍。

算法能力的最小集：**能算复杂度、能选结构、能写出无 bug 的模板、能说清取舍**。

## 二、复杂度：先会算，再会优化

### 2.1 三种记号

| 记号 | 含义 | 用途 |
|---|---|---|
| O(f(n)) | 上界 | 工程上最常用，描述最坏情况 |
| Θ(f(n)) | 紧确界 | 算法分析，描述平均/精确增长 |
| Ω(f(n)) | 下界 | 证明「不可能更快」 |

工程上常把「平均」和「最坏」混着说，面试时要主动区分：`HashMap` 平均 O(1)，最坏 O(n)（哈希碰撞）；`QuickSort` 平均 O(n log n)，最坏 O(n²)。

### 2.2 常见增长阶

| 阶 | n=10⁶ 时的量级 | 典型 |
|---|---|---|
| O(1) | 1 | 哈希查找、数组下标 |
| O(log n) | ~20 | 二分、平衡树、堆调整 |
| O(n) | 10⁶ | 一次遍历 |
| O(n log n) | ~2×10⁷ | 排序、分治 |
| O(n²) | 10¹² | 双重循环、冒泡 |
| O(2ⁿ) | 不可能 | 暴力子集 |

**经验线**：单机 1 秒大约能做 10⁸ 次简单操作。O(n²) 在 n=10⁴ 就是 10⁸，已经到边缘；n=10⁵ 必须换 O(n log n) 或 O(n)。

这条经验线不是让你背数字，而是让你在评审时能快速否掉方案：如果数据量是 100 万，方案里还有一层全量循环里的全量循环，先别谈机器配置。

### 2.3 均摊与空间

- **均摊 O(1)**：`ArrayList` 扩容、`HashMap` 扩容——单次 O(n)，摊到每次插入是 O(1)。
- **空间换时间**：哈希、前缀和、缓存、索引，都是这个交易。
- **递归栈空间**：深度 n 的递归是 O(n) 空间，可能栈溢出；改成迭代或显式栈。
- **常数因子**：O(n) 的链表遍历常比 O(n log n) 的数组排序慢，因为链表节点分散、缓存不友好。别只看阶。

### 2.4 最好、最坏、平均，分别什么时候用

| 口径 | 用途 | 例子 |
|---|---|---|
| 最坏 |  SLA、容量上限、面试复杂度 | 快排最坏 O(n²) |
| 平均 | 日常性能预期 | HashMap 平均 O(1) |
| 均摊 | 连续操作的总成本 | 动态数组扩容 |

对外承诺容量看最坏；做技术选型看平均；解释「为什么单次慢但整体不慢」用均摊。三者混用，评审时一定吵架。

## 三、怎么分析一段代码

### 3.1 嵌套循环：看每层是否真的全量

```java
for (int i = 0; i < n; i++) {          // n
    for (int j = 0; j < n; j++) {      // n
        if (a[i] + a[j] == target) ... // O(1)
    }
}
// O(n²)
```

但如果内层是 `for (int j = i; j < n; j++)`，仍然是 O(n²)，只是常数减半；如果内层每次 `j *= 2`，才是 O(n log n)。

### 3.2 折半：log 从哪里来

```java
while (n > 1) {
    n = n / 2;   // 每次规模减半
}
// O(log n)
```

二分查找、平衡树、堆调整、快速幂，都是「每次把问题规模减半」。看到 `mid`、`/2`、`*2`，先想 log。

### 3.3 递归：先写递推式，再解

```java
T(n) = 2T(n/2) + O(n)   // 归并排序 → O(n log n)
T(n) = T(n-1) + O(1)    // 线性递归 → O(n)
T(n) = 2T(n-1) + O(1)   // 子集枚举 → O(2ⁿ)
```

面试时不需要背主定理，能写出「每层多少个子问题、每个子问题规模、合并成本」就够。

### 3.4 均摊：别被单次操作吓到

`ArrayList.add` 触发扩容时是 O(n)，但每扩容一次容量翻倍，n 次插入的总搬迁次数是 2n，均摊到每次是 O(1)。同理，`HashMap` 扩容也是均摊 O(1)。

### 3.5 空间复杂度也要说

- 递归深度、显式栈、哈希表、结果集，都要算；
- `String` 拼接在循环里会不断创建对象，空间是 O(n²) 级别；
- 流式处理（边读边算）可以把空间从 O(n) 降到 O(1)。

## 四、结构选型：先看操作，再看实现

| 结构 | 查找 | 插入/删除 | 有序 | 典型场景 | Java |
|---|---|---|---|---|---|
| 数组 | O(1) 下标 / O(n) 查找 | 尾部 O(1) 均摊 | 否 | 连续存储、缓存友好 | `ArrayList` |
| 链表 | O(n) | 已知位置 O(1) | 否 | LRU、频繁头尾插入 | `LinkedList` |
| 哈希表 | O(1) 平均 | O(1) 平均 | 否 | 去重、计数、索引 | `HashMap` |
| 跳表 | O(log n) 平均 | O(log n) 平均 | 是 | 排行榜、范围查询 | `ConcurrentSkipListMap` |
| 红黑树 | O(log n) | O(log n) | 是 | 有序映射、定时器 | `TreeMap` |
| B+ 树 | O(log n)（磁盘） | O(log n) | 是 | 数据库索引 | InnoDB |
| LSM 树 | O(log n) 写放大 | O(1) 顺序写 | 是（按 key） | 写多读少、KV 存储 | RocksDB/HBase |
| 堆 | O(1) 取顶 | O(log n) | 部分 | TopK、延迟队列 | `PriorityQueue` |
| Trie | O(k)（k=串长） | O(k) | 前缀 | 敏感词、自动补全 | 自实现 |
| 并查集 | 近 O(1) 均摊 | 近 O(1) | 否 | 连通性、朋友圈 | 自实现 |
| 布隆过滤器 | O(k) | 不支持删除 | 否 | 缓存穿透、去重 | Guava/Redis |
| 位图 | O(1) | O(1) | 是（按位） | 签到、UV 统计 | `BitSet` |
| 环形缓冲 | O(1) | O(1) | 否 | 滑动窗口、日志缓冲 | Disruptor |

**选型三问**：

1. 主要操作是查找、插入还是范围查询？
2. 数据在内存还是磁盘？磁盘要选 B+ 树/LSM，不是红黑树。
3. 是否要求有序/范围/排名？要排序就用树/跳表，别用哈希再排序。

再加一问：**读写比例是多少**？读多写少可以用索引/缓存换查询；写多读少要避免每次写都维护复杂索引，LSM 的写优化就是为这个场景设计的。

## 五、复杂度怎么落到容量上

### 5.1 时间：QPS × 单次操作数

一个接口 QPS 10,000，单请求做 1,000 次比较，就是 10⁷ 次/秒，单机还能扛；如果单请求做 100 万次比较，就是 10¹⁰ 次/秒，必须改算法或分片。

### 5.2 空间：数据量 × 每条记录大小

100 万用户，每条画像 1KB，就是 1GB；如果每个请求都全量加载，内存和 GC 都会崩。先算「常驻内存」和「峰值内存」，再谈缓存。

### 5.3 并发：Little's Law

并发请求数 ≈ QPS × 平均响应时间（秒）。10,000 QPS × 0.5s = 5,000 个并发请求。线程池、连接池、下游配额都按这个量级估，而不是拍脑袋给 200。

复杂度告诉你「单次操作贵不贵」，Little's Law 告诉你「同时有多少次操作」。两者结合，才是容量。

## 六、常见误区

1. **只看阶，不看常数**：O(n) 的链表可能比 O(n log n) 的数组排序慢，因为缓存不友好。
2. **把平均当最坏**：HashMap 平均 O(1)，被构造碰撞时 O(n)；对外承诺要看最坏。
3. **忽略空间**：递归、缓存、结果集都占内存；O(n) 空间在 1GB 限制下可能直接不可行。
4. **用机器掩盖算法**：O(n²) 在 10 万数据下，加机器不如换结构。
5. **过度优化**：n 只有 100 时，O(n²) 和 O(n log n) 差别肉眼不可见，可读性更重要。

## 七、Java 常见操作的复杂度

面试里经常要判断「这段代码到底贵不贵」。下面这张表比背大 O 更实用：

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `ArrayList.get(i)` | O(1) | 连续数组下标 |
| `ArrayList.add(e)` | 均摊 O(1) | 扩容时单次 O(n) |
| `ArrayList.add(0, e)` | O(n) | 全体后移 |
| `LinkedList.get(i)` | O(n) | 从头/尾遍历 |
| `LinkedList.addFirst/Last` | O(1) | 改指针 |
| `HashMap.get/put` | 平均 O(1)，最坏 O(n) | 碰撞退化，树化后 O(log n) |
| `TreeMap.get/put` | O(log n) | 红黑树 |
| `PriorityQueue.offer/poll` | O(log n) | 上浮/下沉 |
| `PriorityQueue.peek` | O(1) | 堆顶 |
| `String +`（循环内） | O(n²) | 每次创建新对象 |
| `String.substring`（Java 7+） | O(n) | 复制底层数组 |
| `StringBuilder.append` | 均摊 O(1) | 扩容翻倍 |
| `Arrays.sort(int[])` | O(n log n) | 双轴快排 |
| `Arrays.sort(Object[])` | O(n log n) | TimSort，稳定 |
| `HashSet.contains` | 平均 O(1) | 哈希 |
| `TreeSet.contains` | O(log n) | 红黑树 |
| `Stream.filter().count()` | O(n) | 惰性 + 终端操作 |

一个常见误判：`for (int i = 0; i < list.size(); i++) list.get(i)` 对 `ArrayList` 是 O(n)，对 `LinkedList` 是 O(n²)。同样是「遍历」，结构不同，复杂度差一个量级。

## 八、从算法复杂度到系统容量

### 8.1 单机上限不是无限的

单机 1 秒约 10⁸ 次简单操作，是量级经验，不是精确承诺。实际受 CPU、内存带宽、cache miss、GC、锁竞争影响，可能差 5–10 倍。做容量估算时留 3–5 倍余量，别按理论峰值承诺 SLA。

### 8.2 扩容是线性的，算法差距不是

- 算法从 O(n²) 降到 O(n log n)，数据量翻倍时差距会继续拉大；
- 加机器只能线性提升吞吐，不能改变复杂度；
- 当单请求复杂度是 O(n²)，加机器只是在延迟爆炸前多撑一会儿。

### 8.3 Amdahl 定律：串行部分决定上限

如果系统有 20% 的逻辑必须串行，即使并行部分无限加速，整体加速比上限是 5 倍。这解释了为什么「加线程」经常没有线性收益：锁、数据库、单点依赖都是串行部分。

### 8.4 尾延迟比平均值更重要

复杂度算的是平均操作数，线上 SLA 看的是 P99/P999。一次 Full GC、一次缓存击穿、一次慢查询，都会让尾延迟远超平均值。容量评估要同时看「平均吞吐」和「尾延迟预算」。

## 九、三个复杂度分析实战

### 9.1 循环里的 contains

```java
for (Order o : orders) {
    if (blacklist.contains(o.getUserId())) { ... }
}
```

`orders` 有 n 条，`blacklist` 是 `ArrayList` 有 m 条：O(nm)。如果 m=10 万、n=10 万，就是 10¹⁰ 次比较。改成 `HashSet` 后 O(n)。

分析步骤：**外层次数 × 内层单次成本**；不要看到「一个 for 循环」就写 O(n)。

### 9.2 循环里的字符串拼接

```java
String s = "";
for (int i = 0; i < n; i++) s += i;
```

每次 `+=` 创建新 String 并复制之前的内容：1+2+...+n = O(n²)。改 `StringBuilder` 是 O(n)。

分析步骤：**看每次操作是否复制了已有数据**；隐式复制是常见的复杂度陷阱。

### 9.3 递归斐波那契

```java
int fib(int n) {
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2);
}
```

递推式 `T(n) = T(n-1) + T(n-2) + O(1)`，解是指数级（约 1.618ⁿ）。原因不是递归本身，而是**重叠子问题**：`fib(n-2)` 被重复计算。加记忆化后 O(n)。

分析步骤：**画递归树**，看同一状态是否被重复访问；重复 → 记忆化/DP。

## 十、下界、NP 与近似：什么时候「更快」不可能

### 10.1 比较排序的下界

基于比较的排序，最坏至少 Ω(n log n)。证明用决策树：n 个元素有 n! 种排列，每次比较只有两个结果，树高至少 log₂(n!) = Θ(n log n)。

这不是「没想到更快的算法」，而是「比较模型下不可能」。要突破，只能利用数据额外结构：计数排序、基数排序、桶排序。

### 10.2 P、NP、NP-complete

- **P**：多项式时间可解；
- **NP**：多项式时间可验证解；
- **NP-complete**：NP 中最难的一类，若有一个多项式解，所有 NP 都能多项式解。

面试常问的 TSP、集合覆盖、SAT 都是 NP-hard。遇到这类问题，不要硬写多项式算法，要：

1. 说明规模小，可用回溯/状压；
2. 用近似算法；
3. 用启发式/贪心；
4. 用整数规划/约束求解器。

### 10.3 近似比

近似算法用「最优解/近似解」的比值衡量。例如：

- 贪心集合覆盖：O(log n) 近似；
- 2-近似 TSP（满足三角不等式）；
- 背包的 FPTAS：误差 ε，复杂度多项式于 n 和 1/ε。

工程上「可接受的近似」往往比「精确但跑不完」更有价值。

## 十一、内存层次与常数：为什么 O(n) 也会慢

### 11.1 缓存行

CPU 一次加载 64 字节缓存行。数组连续访问能命中预取；链表每个节点都可能 cache miss。这就是「同样是 O(n)，数组比链表快几倍」的原因。

### 11.2 局部性

- **空间局部性**：访问相邻内存；
- **时间局部性**：重复访问同一数据。

优化手段：数组代替链表、按行遍历二维数组、分块（tiling）、避免随机跳转。

### 11.3 对象开销

Java 对象有对象头、对齐填充；`Integer` 比 `int` 多 16 字节左右。100 万个 `Integer` 可能占几十 MB，而 `int[]` 只占 4MB。大数组/大集合优先用基本类型或原生库。

### 11.4 常数因子的工程意义

- 同样是 O(n log n)，快排常数比归并小；
- 同样是 O(1)，哈希比数组下标多一次寻址；
- 同样是 O(log n)，B+ 树一次 IO 可能比红黑树 20 次比较还贵。

复杂度决定「量级」，常数决定「同一量级里谁更快」。架构选型两者都要看。

## 面试高频问法

**Q1：怎么判断一个算法能不能扛住线上量级？**

一句话结论：先算单次操作数，再乘 QPS 和峰值倍数，和单机 10⁸ 次/秒的经验线比；超了就换算法、分片或异步。

展开：时间看 QPS × 单请求操作数；空间看数据量 × 单条大小；并发看 QPS × 延迟。三者任一超限，容量就不成立。

加分点：能说出「加机器只能线性扩展，算法差一个阶乘/指数级时加机器无效」。

**Q2：O(n) 一定比 O(n log n) 快吗？**

一句话结论：不一定。要看常数、数据规模、缓存局部性和实际访问模式。

展开：链表遍历是 O(n)，但节点分散、cache miss 高；小数组排序的 O(n log n) 可能更快。n 很小时，低阶算法的常数优势更明显。

加分点：能举出「ArrayList 遍历 vs LinkedList 遍历」的例子。

**Q3：HashMap 为什么平均 O(1)，最坏 O(n)？**

一句话结论：哈希把 key 映射到桶，平均每个桶常数个元素；最坏所有 key 同桶，退化为链表 O(n)。

展开：负载因子 0.75、扩容翻倍、Java 8 链表长度 8 转红黑树，把最坏降到 O(log n)；但仍可能被构造碰撞攻击。

加分点：能说出「扩容是均摊 O(1)，单次 O(n)」。

**Q4：什么情况下用 B+ 树而不是红黑树？**

一句话结论：数据在磁盘、需要范围查询和大规模索引时用 B+ 树；数据在内存、需要有序映射时用红黑树。

展开：磁盘 IO 以页为单位，B+ 树一个节点存几百个 key，树高 3–4 层就能索引亿级数据；红黑树每层一个 key，树高 log₂n，IO 次数多。

加分点：能联系「页大小 16KB、扇出、树高与磁盘 IO 次数」。

## 小结

- **复杂度是工程语言**：先算阶，再看常数与均摊；10⁸ 次操作约等于单机 1 秒。
- **最坏/平均/均摊要分清**：对外承诺看最坏，日常预期看平均，连续操作看均摊。
- **结构选型看操作组合**：查找用哈希，有序/范围用树或跳表，TopK 用堆，前缀用 Trie，连通用并查集。
- **复杂度要落到容量**：时间看 QPS × 操作数，空间看数据量 × 记录大小，并发看 QPS × 延迟。
- **别用机器掩盖算法**：差一个量级还能靠扩容，差一个阶乘/指数级只能换方案。
