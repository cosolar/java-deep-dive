# 海量数据与面试策略：从单机到分布式

> 定位：海量数据题考的不是「背方案」，而是「在内存、时间、精度三个约束下做取舍」。这一篇先讲六类经典问题的解法与边界，再讲面试怎么把「做题」变成「沟通」，最后给一份 30 天训练计划。

## 一、海量数据题的三个约束

拿到题先问三件事：

1. **数据量多大**：10 亿条、每条多大，总容量是否超过内存；
2. **内存/磁盘限制**：可用内存多少，能否多机、能否落盘；
3. **精度要求**：精确、允许近似、允许漏判/误判。

这三个答案不同，方案完全不同。面试官说「内存只有 1GB」，不是让你硬算，是让你承认放不下并给分治/近似方案。

## 二、TopK：堆与分治

### 2.1 单机内存够

小顶堆维护最大的 k 个，流式扫描：

```java
PriorityQueue<Integer> pq = new PriorityQueue<>(k);
for (int x : data) {
    if (pq.size() < k) pq.offer(x);
    else if (x > pq.peek()) {
        pq.poll();
        pq.offer(x);
    }
}
```

时间 O(n log k)，空间 O(k)。求最大 k 个用小顶堆，求最小 k 个用大顶堆。

### 2.2 内存不够

分块：每块读进内存，取块内 TopK；再把所有块的 TopK 归并，取全局 TopK。前提是「全局 TopK 一定在各块 TopK 的并集里」——成立，因为一个元素如果连块内前 k 都进不了，不可能进全局前 k。

### 2.3 数据流

持续追加的场景，维护大小为 k 的堆；如果 k 很大，考虑 Count-Min Sketch + 堆的近似方案。

## 三、去重：布隆过滤器与位图

### 3.1 布隆过滤器

用 k 个哈希函数把元素映射到位数组的 k 个位；查询时所有位都为 1 才「可能存在」。

- 优点：空间极省，查询 O(k)；
- 缺点：有假阳性（不存在判成存在），不支持删除；
- 参数：位数组 m、哈希个数 k、元素数 n，误判率约为 `(1 - e^(-kn/m))^k`。

工程用途：缓存穿透拦截、URL 去重、爬虫已抓取判断。**只能挡「一定不存在」，不能保证「一定存在」**。

### 3.2 位图

对整数范围去重/排序，用 `BitSet` 每个数一位。1 亿个 int 约 12.5MB（1 亿位），远小于 HashSet。限制是数值范围不能太大、不能存重复计数。

### 3.3 精确去重

内存够用 `HashSet`；内存不够用哈希分桶：按 `hash(key) % N` 写到 N 个文件，每个文件单独去重，最后合并。同一个 key 一定落在同一个桶，保证正确性。

## 四、两个大文件求交集/差集

### 4.1 哈希分桶

1. 按 `hash(key) % N` 把两个文件分别切到 N 个子文件；
2. 对每个桶，把小文件读进内存，用 `HashSet` 求交集；
3. 合并所有桶的结果。

关键：**同一个 key 必须落在同一个桶**，所以用同一个哈希函数和桶数。

### 4.2 布隆过滤

如果一个文件远小于另一个，可以把小文件做成布隆过滤器，扫大文件判断「可能存在」，再精确校验。允许假阳性时可直接用；要求精确时，布隆只做预筛。

## 五、排序 100GB：外部排序

### 5.1 三步

1. **分块排序**：每次读一块（如 1GB）进内存，排序后写回磁盘；
2. **多路归并**：用 k 路归并把有序块合并；
3. **输出**：边归并边写最终文件。

### 5.2 关键参数

- 块大小受内存限制；
- 归并路数受文件句柄/缓冲区限制；
- k 越大，比较次数越多但 IO 次数越少；
- 可用「败者树」优化多路比较。

### 5.3 工程替代

能上数据库/Spark 就不要手写外部排序；面试考的是「分块 + 归并」的思路，不是让你实现一个排序系统。

## 六、UV/频率统计：近似算法

### 6.1 HyperLogLog

用哈希值的 leading zeros 估计基数，标准误差约 0.81%，内存只需几 KB 到几十 KB。适合 UV、日活、去重计数；**不能求交集/差集**（HyperLogLog++ 有部分支持）。

### 6.2 Count-Min Sketch

二维计数数组 + 多个哈希函数，更新时对应位置 +1，查询取最小值。空间 O(width × depth)，结果是**高估**，不会低估。适合热点 key、频率 TopK 的预筛。

### 6.3 采样

水库采样（Reservoir Sampling）：流式数据中随机保留 k 个，保证每个元素被选中的概率相等。适合「从超大流中随机抽样」。

```java
int[] reservoir = new int[k];
int i = 0;
for (int x : stream) {
    if (i < k) reservoir[i] = x;
    else {
        int j = random.nextInt(i + 1);
        if (j < k) reservoir[j] = x;
    }
    i++;
}
```

### 6.4 精确 vs 近似

| 需求 | 方案 | 代价 |
|---|---|---|
| 精确 UV | HashSet/位图 | 内存大 |
| 近似 UV | HyperLogLog | 有误差，不能交集 |
| 精确频率 | HashMap | 内存大 |
| 近似频率 | Count-Min Sketch | 高估 |
| 精确去重 | 哈希分桶 | IO 多 |
| 允许假阳性 | 布隆过滤器 | 不能删除 |

## 七、热点 key 与大 key

### 7.1 热点 key

- 本地缓存 + 多级缓存；
- 读写分离/副本；
- 热点 key 拆分（加随机后缀）；
- 限流/降级保护下游。

### 7.2 大 key

- 拆分成多个小 key（hash 分片）；
- 压缩 value；
- 异步删除（`UNLINK`）；
- 避免全量 `HGETALL`，用 `HSCAN` 分批。

### 7.3 缓存穿透/击穿/雪崩

- 穿透：布隆过滤器 + 空值缓存；
- 击穿：互斥重建 + 逻辑过期；
- 雪崩：过期时间随机 + 多级缓存 + 降级。

## 八、面试策略：把「做题」变成「沟通」

### 8.1 五步答题

1. **澄清**：输入规模、数据范围、是否有序、是否允许重复、内存限制；
2. **给暴力解**：说明复杂度，确认方向；
3. **优化**：换结构（哈希/堆/二分）或换思路（双指针/DP/分治）；
4. **写代码**：先写边界与函数签名，再写主体；变量名有意义；
5. **自测**：空、单元素、全相同、极值、溢出；
6. **复杂度**：时间/空间都说，常数因子与均摊也提。

### 8.2 常见扣分点

- 不澄清就写，写完发现数据量根本不适用；
- 边界不处理：空数组、单元素、全相同；
- 递归爆栈、`int` 溢出；
- 复杂度说错，或者只说时间不说空间；
- 代码写完不自测，面试官一跑就挂；
- 过度设计：n 只有 100，非要上分布式。

### 8.3 题型地图

| 题型 | 首选方法 | 关键点 |
|---|---|---|
| 两数/三数之和 | 双指针/哈希 | 去重、排序 |
| 最长/最短子数组 | 滑动窗口 | 收缩条件 |
| 区间求和 | 前缀和 | `prefix[0]=0` |
| 查找/答案单调 | 二分 | 下界模板 |
| 链表操作 | 哑节点 + 画图 | 边界 |
| 缓存设计 | HashMap + 双向链表 | O(1) |
| TopK/第 k | 堆/Quickselect | 方向别反 |
| 树的遍历 | 递归/栈/Morris | 栈深 |
| 依赖/课程表 | 拓扑排序 | 环检测 |
| 最短路 | BFS/Dijkstra | 边权 |
| 最优子结构 | DP | 状态定义 |
| 海量数据 | 分治/哈希分桶/近似 | 约束优先 |

| 周 | 重点 | 每天 |

## 九、容量与精度估算

### 9.1 布隆过滤器的参数

给定 n 个元素、允许误判率 p：

```text
m = -n * ln(p) / (ln2)^2      // 位数组长度
k = (m / n) * ln2             // 哈希函数个数
```

例：n = 1 亿，p = 1%，则 m ≈ 9.58 亿位 ≈ 120MB，k ≈ 7。若 p = 0.1%，m 约 180MB。**误判率降一个数量级，内存涨约 50%。**

工程上不要自己推公式，用 Guava `BloomFilter` 或 RedisBloom，但要知道「内存与误判率的交换关系」。

### 9.2 HyperLogLog 的误差

标准 HLL 的相对误差约 `1.04 / sqrt(m)`，m 是寄存器个数。m = 16384 时误差约 0.81%，内存约 12KB。Redis 的 HLL 上限 12KB。

### 9.3 外部排序的缓冲区

多路归并时，每个输入块需要一个读缓冲区，输出一个写缓冲区。k 路归并的内存约 `(k+1) × bufferSize`；k 受内存和文件句柄限制。不是「k 越大越好」。

### 9.4 采样与置信度

水库采样 k 个，估计总量/比例时有误差；k 越大误差越小。面试时如果被问「采样 1000 个够不够」，要回答「取决于要求的置信区间，不是拍脑袋」。

## 十、数据倾斜与分桶

### 10.1 倾斜从哪来

- 哈希函数不均匀；
- 某些 key 天然巨大（大卖家、大 V、热点商品）；
- 分片键选错（按用户分片，但查询按商家）。

### 10.2 处理办法

| 场景 | 办法 |
|---|---|
| 大 key | 拆 key（加后缀）、分桶 |
| 热点用户 | 单独分片/副本 |
| 分片键查询错位 | 异构索引表（ES/宽表） |
| 聚合倾斜 | 两阶段聚合（局部预聚合 + 全局合并） |
| 无法拆分 | 限流/异步/降级 |

两阶段聚合：先按 `key + 随机后缀` 做局部聚合，再去掉后缀做全局聚合。多一次 shuffle，但解决单点。

### 10.3 分桶的纪律

- 同一个 key 必须落同一个桶（否则结果错）；
- 桶数要保证单桶能进内存；
- 哈希函数要稳定，不能每次运行变；
- 桶文件要能清理，避免磁盘打满。

## 十一、一道海量数据题的完整推演

**题目**：10 亿条订单日志，每条约 200B，找金额最高的 100 笔，内存 2GB。

### 11.1 先算约束

- 10 亿 × 200B = 200GB，远大于 2GB，不能全量加载；
- 只求 Top100，不需要全排序；
- 金额可能重复，需要保留订单 ID。

### 11.2 方案

1. 顺序读文件，维护大小为 100 的小顶堆（按金额）；
2. 每条日志与堆顶比较，比堆顶大就替换；
3. 内存 O(100)，时间 O(n log 100)；
4. 如果日志分散在多个文件，每个文件先取 Top100，再对 100×文件数 归并。

### 11.3 追问

- **金额相同怎么办**：堆比较器加订单 ID，保证稳定/可复现；
- **数据有坏行**：解析失败跳过并计数，不要整批失败；
- **要 Top100 且按金额排序输出**：最后对 100 个元素排序；
- **内存只有 100KB**：堆仍可行（100 条），但读缓冲要小；
- **要精确去重后 Top100**：先按订单 ID 去重（哈希分桶），再 TopK。

### 11.4 答题结构

1. 复述约束，确认数据量/内存/精度；
2. 给暴力解（全量排序）及为什么不可行；
3. 给可行解（堆/分治），算复杂度与内存；
4. 给边界与追问；
5. 说明工程实现（流式读、异常处理、监控）。

## 十二、完整推演：100 亿 URL 去重，内存 1GB

**题目**：100 亿条 URL，每条平均 100B，内存 1GB，求不重复 URL 的数量。

### 12.1 先算约束

- 原始数据 100 亿 × 100B = 1TB，不能全量加载；
- 即使只存 64 位哈希，100 亿 × 8B = 80GB，仍放不下；
- 允许近似还是精确？题目说「不重复数量」，通常要求精确；如果允许误差，可用 HLL。

### 12.2 精确方案：哈希分桶

1. 用稳定哈希 `h = hash(url)`，按 `h % N` 把 URL 写到 N 个文件；
2. 同一个 URL 必落同一个桶；
3. 逐个桶读进内存，用 `HashSet` 去重并计数；
4. 汇总所有桶的计数。

桶数怎么定：单桶数据量 ≈ 1TB / N，要小于可用内存（留出 HashSet 开销，通常按 2–3 倍余量）。N = 2000 时单桶约 500MB，加开销可能仍紧；N = 4000 更稳。

### 12.3 哈希冲突怎么办

- 只用哈希去重会误判（不同 URL 同哈希）；
- 桶内 `HashSet` 存完整 URL，保证精确；
- 如果 URL 太长，可存「哈希 + 长度 + 前 16 字节」做预筛，相等再比对原文；
- 不要用 `hash % N` 的 Java `hashCode`，字符串哈希可能被构造碰撞，用 MurmurHash/xxHash。

### 12.4 近似方案：HyperLogLog

如果只要「大约多少」，用 HLL：

- 每个桶一个 HLL，内存几 KB；
- 合并各桶 HLL（HLL 可合并）；
- 误差约 0.8%，内存从 GB 降到 MB。

答题时要说清「精确 vs 近似」的取舍，不要一上来就 HLL。

## 十三、分布式海量处理：把单机方案放大

### 13.1 MapReduce 的映射

- Map：分桶/局部 TopK/局部去重；
- Shuffle：按 key 分区；
- Reduce：全局聚合/归并。

单机的「哈希分桶」在分布式就是 `partitionBy(key)`；单机的「多路归并」就是 Reduce 端的合并。

### 13.2 Spark/Flink 的注意点

- shuffle 是最贵的阶段，能 map-side 聚合就先聚合；
- 数据倾斜用加盐/两阶段聚合；
- 大 key 单独处理；
- 检查点/状态大小，避免 OOM。

### 13.3 分布式 TopK

1. 每个分区取 TopK；
2. 汇总到 Driver/Reduce 再取 TopK；
3. K 很小时，汇总数据量 = 分区数 × K，可接受。

### 13.4 流式去重

- 布隆过滤器做预筛；
- 精确去重靠外部存储（Redis/DB）或窗口内状态；
- 跨窗口去重要考虑状态过期与内存。

## 十四、面试对话示例：把思路讲出来

**面试官**：10 亿条日志找 Top100，内存 1GB，怎么做？

**你**：先确认一下，日志是单文件还是多文件？金额是否有重复？需要精确 Top100 还是允许近似？

**面试官**：单文件，金额可能重复，要精确。

**你**：那全量排序不可行，10 亿条按 200B 算约 200GB。我的方案是流式读，维护一个 100 容量的小顶堆：每条和堆顶比较，比堆顶大就替换；时间 O(n log 100)，内存 O(100)。如果文件分块，可以先每块取 Top100 再归并。

**面试官**：金额相同怎么办？

**你**：比较器加订单 ID，保证结果稳定可复现；如果要按金额降序输出，最后对 100 条排序。

**面试官**：如果内存只有 10MB 呢？

**你**：堆仍然只需要 100 条，10MB 足够；但读缓冲要调小，避免一次读太多。如果是多文件且单文件很大，按块读，每块取 Top100，再归并。

**面试官**：如果要求去重后 Top100？

**你**：先按订单 ID 哈希分桶去重，再在每个桶内取 Top100，最后归并；分桶保证同一 ID 落同一桶，结果是精确的。

这个对话的关键：**先澄清、再算约束、给方案、主动补边界**。不要一上来写堆代码。

## 十五、面试高频问法

**Q1：10 亿个数找最大的 100 个，内存只有 1GB，怎么做？**

一句话结论：小顶堆维护 100 个元素，流式扫描，O(n log 100)、O(100) 内存；数据在文件就分批读。

展开：若数据分散在多个文件，各文件先取 Top100 再归并；不要全量排序，也不要加载全量。

加分点：能估算「10 亿 × 8B ≈ 8GB，放不进内存」并给出分治方案。

**Q2：布隆过滤器为什么会误判，能不能删除？**

一句话结论：多个哈希位可能被其他元素置 1，所以「可能存在」可能是假阳性；位是共享的，删除会影响其他元素，标准布隆不支持删除。

展开：误判率随元素数增加而上升；需要删除用计数布隆/布谷鸟过滤器。

加分点：能说出「布隆只能挡一定不存在，不能保证一定存在」。

**Q3：两个大文件求交集，内存不够怎么办？**

一句话结论：哈希分桶，同一个 key 落同一个桶，逐桶读入内存求交集，再合并。

展开：桶数要保证单桶能放进内存；哈希函数和桶数对两个文件必须一致。

加分点：能说出「小文件可先做布隆预筛，再精确校验」。

**Q4：100GB 数据排序怎么做？**

一句话结论：分块读入内存排序写回，再多路归并；块大小受内存限制，归并路数受文件句柄限制。

展开：可用败者树优化多路比较；能上 Spark/数据库就不手写。

加分点：能说出「外部排序的瓶颈是 IO，不是比较」。

**Q5：HyperLogLog 和精确 UV 怎么选？**

一句话结论：要精确用 HashSet/位图，内存大；允许约 0.8% 误差用 HLL，内存几 KB。

展开：HLL 不能求交集/差集；Count-Min Sketch 适合频率且高估。

加分点：能说出「UV 统计的精度要求和成本 trade-off」。

**Q6：面试时不会做怎么办？**

一句话结论：先澄清、给暴力解、说复杂度，再逐步优化；把思考过程讲出来，比沉默强。

展开：可以问「数据量多大」「是否有序」「能否用额外空间」；即使没写出最优解，清晰的暴力解 + 优化方向也能得分。

加分点：能说出「面试考的是沟通与边界，不是背题量」。

## 小结

- **海量数据先问约束**：数据量、内存、精度；约束决定方案。
- **TopK 用堆**，内存不够就分块取 TopK 再归并；O(n log k)。
- **去重用布隆/位图/哈希分桶**：布隆有假阳性、不能删除；精确去重靠分桶。
- **大文件交集用哈希分桶**，同 key 同桶；小文件可布隆预筛。
- **外部排序 = 分块排序 + 多路归并**，瓶颈在 IO。
- **UV/频率可用 HLL/Count-Min Sketch**，接受误差换空间。
- **面试是沟通**：澄清 → 暴力 → 优化 → 代码 → 自测 → 复杂度。
