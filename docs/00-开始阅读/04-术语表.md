# 术语表

> 定位：一套跨 20 个板块的缩写与术语速查表。读文章遇到不认识的缩写，先来这里查一句话定义，再回原文看上下文。术语按领域分组，不追求学术严谨，追求「面试时能一句话说清」。

## 一、Java 与 JVM

| 术语 | 全称 / 英文 | 一句话解释 |
|---|---|---|
| JVM | Java Virtual Machine | 执行字节码的虚拟机，屏蔽操作系统差异，提供 GC、JIT、类加载等能力 |
| JMM | Java Memory Model | Java 内存模型，规定多线程下共享变量的可见性、有序性与 happens-before 规则 |
| JIT | Just-In-Time Compiler | 运行时把热点字节码编译成本地机器码，C1 负责快启动、C2 负责高优化 |
| GC | Garbage Collection | 垃圾回收，自动回收不可达对象；重点是「怎么判定垃圾」和「什么时候 STW」 |
| STW | Stop The World | GC 时暂停所有应用线程的阶段，是延迟毛刺的主要来源 |
| OOM | Out Of Memory Error | 内存耗尽错误，可能发生在堆、Metaspace、直接内存或线程栈 |
| Metaspace | Metaspace | JDK 8+ 的类元数据区，位于本地内存，替代 PermGen |
| TLAB | Thread Local Allocation Buffer | 线程私有的堆内分配缓冲区，减少分配时的锁竞争 |
| CAS | Compare-And-Swap | 比较并交换的原子指令，是 AQS、原子类、无锁队列的基础 |
| AQS | AbstractQueuedSynchronizer | JUC 的同步器框架，用 state + CLH 队列实现锁与信号量 |
| JUC | java.util.concurrent | Java 并发工具包，包含线程池、并发容器、同步器、原子类 |
| JMM 可见性 | Visibility | 一个线程的写何时能被另一个线程看到，靠 volatile、锁、final 等保证 |
| happens-before | Happens-Before | JMM 定义的偏序关系，前者结果对后者可见，是判断并发出错的依据 |
| ThreadLocal | Thread Local Variable | 线程私有变量，底层是 ThreadLocalMap；线程池下不 remove 会泄漏 |
| TTL | TransmittableThreadLocal | 阿里开源的 ThreadLocal 增强，解决线程池/异步任务中的上下文传递 |
| 虚拟线程 | Virtual Thread | JDK 21 正式特性，由 JVM 调度的轻量线程，适合高并发 IO 阻塞场景 |
| Record | Record Class | JDK 16 正式的特性，不可变数据载体，自动生成构造器、equals、hashCode |
| Sealed Class | Sealed Class | JDK 17 正式的特性，限制哪些类可以继承/实现它 |
| AOT | Ahead-Of-Time Compilation | 构建期编译，Spring AOT 用于生成 Native Image 所需的元数据 |
| GraalVM | GraalVM | 支持 Native Image 的 JDK 发行版，把 Java 应用编译成原生可执行文件 |
| JFR | Java Flight Recorder | 低开销的运行时事件记录器，用于 GC、锁、IO、异常分析 |
| JNI | Java Native Interface | Java 调用本地代码的接口，Netty、压缩库、加密库常用 |

|---|---|---|

| AOP | Aspect-Oriented Programming | 面向切面编程，把日志、事务、权限等横切逻辑从业务代码中剥离 |
| Bean | Spring Bean | 由 Spring 容器管理的对象，经历实例化、属性填充、初始化、代理等生命周期 |
| 三级缓存 | Three-Level Cache | Spring 解决单例循环依赖的机制：singletonObjects / earlySingletonObjects / singletonFactories |
| MVC | Model-View-Controller | 分层 Web 模式；Spring MVC 的核心是 DispatcherServlet 与 HandlerMapping |
| SPI | Service Provider Interface | 服务提供者接口，JDK 与 Dubbo、Spring Boot 都用它做扩展发现 |
| ORM | Object-Relational Mapping | 对象关系映射，JPA/Hibernate/MyBatis 都属于这一层 |
| JPA | Jakarta Persistence API | Java 持久化规范，Hibernate 是主流实现 |
| N+1 | N+1 Query Problem | 查 1 条主记录后又逐条查 N 次关联数据，ORM 最常见的性能坑 |

| 脏检查 | Dirty Checking | Hibernate 在 flush 时对比快照，自动生成 UPDATE |
| 连接池 | Connection Pool | 复用数据库连接的池子，HikariCP、Druid 是主流实现 |
| 乐观锁 | Optimistic Lock | 假设冲突少，提交时用版本号/CAS 检查，冲突则失败重试 |
| 悲观锁 | Pessimistic Lock | 假设冲突多，先 `SELECT ... FOR UPDATE` 锁住再操作 |
| WebFlux | Spring WebFlux | Spring 的响应式 Web 框架，基于 Reactor + Netty，非阻塞 |
| 背压 | Backpressure | 消费者告诉生产者「慢一点」的机制，响应式流的核心 |
| AOT 提示 | Runtime Hints | 告诉 GraalVM Native Image 哪些反射/资源/JNI 需要保留的元数据 |

## 三、数据库

| 术语 | 全称 / 英文 | 一句话解释 |
|---|---|---|
| ACID | Atomicity/Consistency/Isolation/Durability | 事务四大特性：原子、一致、隔离、持久 |
| MVCC | Multi-Version Concurrency Control | 多版本并发控制，读不加锁、读写不互斥；MySQL 用 undo，PostgreSQL 用堆内多版本 |
| WAL | Write-Ahead Log | 先写日志再写数据页，保证崩溃恢复；MySQL 的 redo log 就是 WAL |
| redo log | Redo Log | InnoDB 的物理重做日志，保证已提交事务不丢 |
| undo log | Undo Log | InnoDB 的逻辑回滚日志，支撑事务回滚与 MVCC 快照读 |
| binlog | Binary Log | MySQL Server 层的逻辑日志，用于主从复制与 CDC |
| 回表 | Back to Table | 二级索引查到主键后，再回聚簇索引取整行 |
| 覆盖索引 | Covering Index | 查询列都在索引里，不需要回表 |
| 最左前缀 | Leftmost Prefix | 联合索引按定义顺序匹配，跳过前导列通常用不上索引 |
| 间隙锁 | Gap Lock | 锁住索引记录之间的开区间，RR 下防幻读，也降低并发 |
| Next-Key Lock | Next-Key Lock | Record Lock + Gap Lock，左开右闭，InnoDB RR 的默认行锁 |
| 幻读 | Phantom Read | 同一事务两次范围查询，第二次多出别的事务插入的行 |
| 隔离级别 | Isolation Level | RU / RC / RR / Serializable，MySQL 默认 RR |
| 两阶段提交 | Two-Phase Commit | 事务消息/分布式事务的提交协议：prepare + commit |
| 分库分表 | Sharding | 把单库单表按规则拆到多库多表，解决容量与写入瓶颈 |
| 冷热分离 | Hot/Cold Separation | 热数据留在高性能存储，冷数据归档到低成本存储 |
| CDC | Change Data Capture | 变更数据捕获，常见实现是解析 binlog（Canal/Debezium） |
| OLTP | Online Transaction Processing | 面向交易的联机事务处理，强调低延迟与一致性 |
| OLAP | Online Analytical Processing | 面向分析的联机分析处理，强调大范围扫描与聚合 |
| HTAP | Hybrid Transactional/Analytical Processing | 交易与分析混合负载，TiDB、OceanBase 是代表 |

## 四、分布式与中间件

| 术语 | 全称 / 英文 | 一句话解释 |
|---|---|---|
| CAP | Consistency/Availability/Partition tolerance | 分区容忍下，一致性与可用性不可兼得；分布式系统必须选 P |
| BASE | Basically Available/Soft state/Eventually consistent | 最终一致性实践原则，是 CAP 的工程折中 |
| Raft | Raft Consensus | 易理解的共识算法，通过选举、日志复制、任期保证一致 |
| Paxos | Paxos | 经典共识算法，Raft 的思想源头之一 |
| Quorum | Quorum | 多数派机制，写成功需要超过半数节点确认 |
| 脑裂 | Split Brain | 集群分裂成多个自认为主的分区，可能双写造成数据错乱 |
| Lease | Lease | 带过期时间的授权，用于选主与分布式锁的租约 |
| 2PC | Two-Phase Commit | 分布式事务的强一致协议，性能与可用性代价高 |
| 3PC | Three-Phase Commit | 2PC 的改进，增加 pre-commit 阶段，仍无法完全避免阻塞 |
| TCC | Try-Confirm-Cancel | 业务层补偿型分布式事务，三个方法都要幂等 |
| Saga | Saga | 长事务拆成多个本地事务，失败时按反向补偿 |
| Outbox | Transactional Outbox | 本地事务 + 消息表，保证业务与消息发送的最终一致 |
| 幂等 | Idempotency | 同一请求执行多次，结果与执行一次一致 |
| 分布式锁 | Distributed Lock | 跨进程互斥，Redis/ZooKeeper/数据库都可实现，关键在续期与误删防护 |
| 限流 | Rate Limiting | 控制单位时间请求量，常见算法：计数器、滑动窗口、令牌桶、漏桶 |
| 熔断 | Circuit Breaker | 下游故障时快速失败，避免级联雪崩 |
| 隔离 | Bulkhead | 按资源池隔离，防止一个依赖拖垮全部线程 |
| AMQP | Advanced Message Queuing Protocol | RabbitMQ 使用的消息协议，核心是 Exchange/Queue/Binding |
| ISR | In-Sync Replicas | Kafka 中与 Leader 保持同步的副本集合 |
| Offset | Offset | Kafka 分区内消息的位置编号，消费者提交位点 |
| Consumer Group | Consumer Group | Kafka 的消费组，组内分区互斥、组间广播 |
| DLQ | Dead Letter Queue | 死信队列，存放重试耗尽或无法消费的消息 |
| Exactly-Once | Exactly-Once Semantics | 端到端精确一次，Kafka 事务 + 幂等生产者 + 消费端去重共同保证 |
| HNSW | Hierarchical Navigable Small World | 近似最近邻向量索引，多层图结构，召回与延迟平衡好 |
| IVF | Inverted File Index | 倒排文件索引，先聚类再在少数簇内搜索 |
| BM25 | Best Matching 25 | 经典文本相关性算法，TF-IDF 的改进版 |
| RRF | Reciprocal Rank Fusion | 倒数排名融合，把多路召回结果按排名合并，无需调权重 |

## 小结

- 术语只在上下文里有意义，别孤立背定义；看到一个词，回到对应文章看它解决什么问题。
- 面试表达优先说「它解决什么问题、代价是什么」，而不是背英文全称。
- 同一术语在不同生态含义可能不同（如 Shuffle 在 Spark 与 Kafka 中不是一回事），以文章上下文为准。
- 新增术语请按领域补到对应表格，保持「一句话解释」的密度。
